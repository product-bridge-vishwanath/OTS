<Section kind="story">

A team's deploy pipeline had one job: run tests, then deploy if they pass. For four months it worked exactly as described. Then a deploy went out with a test suite that had been silently failing for two weeks — the pipeline's status checks showed green the entire time.

The cause, once found, was almost funny: a dependency update had changed how their test runner reported its exit code on a specific kind of failure, so the test process was crashing *before* it finished running — and the CI step that ran it was written as `npm test || true`, added eight months earlier by someone fixing an unrelated flaky-test annoyance, which swallowed every possible failure from that command, forever, silently, including the kind nobody intended to suppress.

Nobody had read that line in eight months because it had never been the subject of an incident. The pipeline wasn't broken; it was doing exactly what `|| true` says: "no matter what happens here, report success." Green had stopped meaning "tests passed" and started meaning "the step ran," and nobody had updated their trust in the color to match.

</Section>

<Section kind="already-did">

You've pushed code and watched a little status indicator — a spinner, then a green check or a red X — without necessarily knowing what ran in between, or where. If you've set up a project on Vercel, Render or similar, you've almost certainly triggered a build-and-deploy pipeline without writing a single line of CI configuration yourself, because the platform wired up its own default version the moment you connected a repo.

This lesson is about the version you *do* configure — the one with a file you can read, that runs exactly the steps it says and no others, which is both more powerful and more capable of quietly lying to you than a platform's built-in default.

</Section>

### What CI/CD actually is: scripted steps, on someone else's computer, triggered by git

<Term k="ci-cd">CI/CD</Term> is not a product — it's a **pipeline**: a sequence of commands, run automatically on a trigger (usually a push or a pull request), on a machine you don't own, that reports back pass or fail. Continuous Integration is the "run tests/checks on every change" half; Continuous Deployment is the "and then ship it" half. Plenty of real setups do CI without CD — tests run automatically, deploys stay manual — and that's a legitimate, common choice, not a half-finished pipeline.

### Anatomy of a real workflow file

```yaml
# .github/workflows/ci.yml — this exact file exists in this project's repo.
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-lint:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the repo
        uses: actions/checkout@v4
      - name: Set up Node
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"
      - name: Install dependencies
        run: npm ci
      - name: Lint content
        run: npm run lint:content
      - name: Build
        run: npm run build
```

| Part | Means |
|---|---|
| `on:` | What triggers this — here, every push to `main` and every PR targeting it |
| `jobs:` | One or more independent units of work (can run in parallel) |
| `runs-on:` | What machine — a fresh, ephemeral VM every single run |
| `steps:` | Run in order, top to bottom; any non-zero exit stops the job as failed |
| `uses:` | A pre-built, reusable action (checkout, setup-node) rather than a raw shell command |
| `run:` | A literal shell command — this is where `|| true` or any other exit-code manipulation hides |

<Callout type="key">
**Every CI run starts from nothing.** No files from your last run, no installed dependencies, no cached anything — unless you explicitly fetch/install/cache them in the workflow itself. This is *why* `actions/checkout` and `npm ci` (not `npm install`) are the first real steps: the runner genuinely has none of your code or dependencies until those steps put them there. `npm ci` specifically installs exactly what the lockfile says, failing loudly if the lockfile and `package.json` disagree — the correct choice for CI, where reproducibility matters more than convenience.
</Callout>

### `npm ci` vs `npm install`, and why it matters here specifically

`npm install` can *update* the lockfile to satisfy `package.json`; `npm ci` refuses to and fails instead if they're out of sync, then installs from the lockfile exactly as written. In CI, that difference is the entire point: you want the build to fail loudly if someone's dependency change wasn't properly locked, not to silently resolve it differently on every run.

### Secrets in CI: a different trust boundary than your laptop

A CI runner needs credentials to do real things (deploy, call an API) without those credentials ever appearing in your repo's files. GitHub Actions' `secrets` context exists for exactly this: values stored encrypted on the platform, injected as environment variables at runtime, and — critically — **masked in logs**, so even an accidental `echo $SECRET` prints `***` rather than the real value in the visible output (though it's still technically present in the runner's environment, which is why a step that deliberately exfiltrates it, e.g. by sending it to an external URL, is a different and real risk category).

```yaml
steps:
  - name: Deploy
    env:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
    run: ./deploy.sh
```

This is M1.5's environment-variable precedence lesson, one more layer out: the CI platform's secret store is simply another source in the chain, and — as M1.2's break-fix already showed — a renamed secret becomes an **empty string**, not an error, in exactly the same way here.

<Section kind="break-fix">

**Symptom:** A deploy goes out with a broken feature. CI was green on the merge commit. The developer insists "the pipeline passed, so how could this happen" — and is right that it passed, and wrong that passing meant what they assumed.

<Evidence title="the actual CI config">

```yaml
jobs:
  test:
    steps:
      - run: npm ci
      - run: npm test || true    # added 8 months ago, see commit a1b2c3d
      - run: npm run build
  deploy:
    needs: test
    steps:
      - run: ./deploy.sh
```

</Evidence>

<Evidence title="the commit that added the problematic line, found via `git log -S`">

```text
commit a1b2c3d
    "fix flaky test suite blocking deploys — one test intermittently
     times out on the CI runner, not a real failure. Temporary
     workaround until we fix the underlying flakiness."
```

</Evidence>

<Evidence title="test output from the failing run, buried in the logs">

```text
FAIL  src/checkout.test.js
  ✕ applies discount correctly (12 ms)
    Expected: 45
    Received: 50

Tests: 1 failed, 23 passed, 24 total
```

(exit code from `npm test`: 1 — but the step shows green, because of `|| true`)

</Evidence>

A real test genuinely failed, with a clear, specific, correct failure message sitting in the logs. Why did the pipeline report success anyway, and whose decision, eight months ago, is actually responsible?

<Reveal label="Reveal the cause">

**`npm test || true` makes this step's exit code always 0, regardless of what `npm test` itself reports — the pipeline is not lying or malfunctioning; it is executing exactly the instruction it was given, which happens to mean "ignore every test failure, forever," not the narrower "ignore one specific flaky test" that the commit message describes.**

**The gap between intent and implementation is the entire story.** The commit message says "one test intermittently times out" — a specific, scoped problem. The fix applied is `|| true` on the *entire test command* — an unscoped, total suppression of every test's result, forever, including the real, correct, specific discount-calculation failure that appeared eight months later. The author solved today's specific annoyance with a tool broad enough to also solve (by silencing) every future test failure of any kind, and nobody revisited the line since nothing had gone wrong with it — which is exactly the problem: it couldn't *visibly* go wrong, by construction.

**Why "the pipeline passed, so how could this happen" is both an understandable and a wrong inference:** it conflates "the pipeline reported success" with "the thing the pipeline is supposed to verify (tests passing) is true." Those were the same fact for eight months, until the day they weren't, and nothing about the pipeline's *output* (green) distinguished the two days from each other — the distinction only existed in the actual logs, which nobody was reading because green meant "no need to look."

**The fix, correctly scoped this time:**
```yaml
- run: npm test -- --testPathIgnorePatterns="specific-flaky-test.test.js"
# or, better: fix the actual flakiness (often a timing/retry issue in
# the test itself), or mark that ONE test as .skip with a tracking
# issue — never silence the whole suite for one test's problem.
```

And separately, as a structural fix regardless of this specific incident: **audit every `|| true` / `continue-on-error: true` in any CI config**, on a recurring basis, and require each one to carry a comment explaining exactly what it's suppressing and why — a line with no stated reason is a line nobody can tell apart from this exact failure mode until it's already caused one.

**The transferable rule:** **a CI check's color only means what its underlying commands actually verify — not what its name or history implies.** "Green" is a claim about exit codes, and exit codes can be overridden by anyone with write access to the workflow file, for a reason that seemed narrow and scoped at the time and silently widened into "ignore everything" the moment it was written broadly instead of specifically.

</Reveal>

</Section>

<Section kind="checklist">

For any CI/CD pipeline you rely on:

- Does every step's reported pass/fail genuinely reflect the underlying command's real exit code?
- Search explicitly for `|| true`, `|| exit 0`, `continue-on-error: true` — for every hit, is there a clear, current, correctly-scoped reason?
- Does the pipeline use `npm ci` (or your language's equivalent reproducible-install command), not a convenience install that can silently drift from the lockfile?
- Are secrets referenced through the platform's secret store, never hardcoded in the workflow file itself?
- Can you reproduce any CI failure by running the exact same commands locally?

What good looks like: "CI is green" is trusted exactly as much as the specific steps it runs — no more, no less — and everyone on the team could state, precisely, what green does and does not verify for this specific pipeline.

Red flags: an exit-code suppression with no comment explaining why; "the pipeline passed" treated as proof of correctness beyond what the pipeline's own steps actually check; a CI failure nobody can reproduce locally.

</Section>
