<Section kind="story">

A founder asked his agent to "fix the slow dashboard query." It came back with a diff: twelve lines changed, one new index added, one query rewritten. He read the top three lines, saw `CREATE INDEX`, recognized it from M6.1, and approved it — the dashboard was noticeably faster in his own testing within the hour.

He hadn't read line nine, which quietly removed a `WHERE user_id = $1` clause from the rewritten query "because it was redundant with the new index" — a claim that was true for *performance* and catastrophically false for *correctness*: that clause was the only thing scoping the dashboard's results to the logged-in user. Every user who loaded their dashboard for the next six days saw every other user's data, mixed in with their own, sorted by whatever the new index happened to prefer.

Nobody had reviewed the diff as a whole — a twelve-line change had been approved as "the three lines I recognized," and the other nine lines got the credibility of the three without anyone actually reading them.

</Section>

<Section kind="already-did">

You've approved a pull request — your own agent's, or a human contributor's — by skimming the summary, glancing at the file names, and clicking merge. You've probably done this specifically *because* reading unfamiliar code line by line feels slow and the summary sounded reasonable. M2.2 gave you the tools to find a bug once it exists; this lesson is about catching it before it ships, in a diff someone else (or something else) wrote.

</Section>

### Reading a real diff, line by line, as evidence

```diff
-      - "3000:3000"
+      - "3001:3000"
```

Read this exactly as it's written: a line was **removed** (`-`), a line was **added** (`+`), and together they say "the host port changed from 3000 to 3001; the container's own port, 3000, is unchanged." Every diff is this same grammar — `-` is "no longer true," `+` is "now true," and unmarked context lines are "unchanged, shown so you can see where you are."

<Callout type="key">
**Read every removed line as carefully as every added one.** The story's bug was in a `-` line, not a `+` line — people instinctively scrutinize what's being *added* as the "new, risky part" and skim what's being *removed* as presumably safe to lose. A removed `WHERE` clause, a removed validation check, a removed `await` — deletions are exactly as capable of introducing a bug as additions, and they get systematically less attention.
</Callout>

### The checklist that would have caught the story's bug

| Check | What it would have shown |
|---|---|
| Does the diff's scope match the request? | "Fix the slow query" touching the query's WHERE clause, not just adding an index — worth a second look |
| Is every REMOVED line's purpose understood, not just every added one? | The `WHERE user_id = $1` deletion, read carefully, removes authorization scoping, not just a redundant filter |
| Does any claim in the PR description ("redundant with the index") hold up to checking? | An index can make a lookup fast; it cannot make a `WHERE` clause's *authorization* role redundant — those are different jobs that happened to share one line of SQL |
| Would this pass the demo app's existing tests, if any exist for this path? | A test asserting "user A cannot see user B's dashboard data" would have failed immediately — its absence is itself a finding |

### Red flags, specifically for agent-generated diffs

- **A fix for symptom X that also touches authorization, validation, or error handling** "while I was in there" — scope creep is a review risk regardless of who wrote it, and agents do it readily when asked to "also clean up nearby code."
- **A confident claim in the description that isn't actually checkable from the diff** — "this is safe because X" is a claim to verify, not a reason to skip verifying.
- **New dependencies added for a change that didn't obviously need one.**
- **Any `.env`, secrets, or CI config file touched** when the request was about application logic.

<Section kind="tools">

| Need | Tool |
|---|---|
| Read a diff's shape before its content | `git show --stat`, or a PR's "Files changed" summary tab before the line-by-line view |
| Side-by-side diff view | GitHub/GitLab's PR interface, or `git difftool` |
| Find every caller of a function before trusting "this is safe to change" | Your editor's "find references," or `grep -rn "functionName("` |
| Verify a specific claim in a PR description | Actually run the code, or write the test the description implies should pass |

What good looks like: every merged diff's scope was checked against its stated purpose before the content was read; every removed line got read as carefully as every added one; and a confident claim in a description ("this is safe because...") was verified, not trusted.

</Section>

<Section kind="hands-on">

1. **Pick a real commit from a repo you have** (this project's own history works) and run the three-question scope check *before* reading the diff's content line by line. Write down your answers.

2. **Then read the content**, including every removed line, as carefully as the added ones.

3. **Reproduce the story's bug pattern yourself.** Write a tiny function with a `WHERE`-clause-style authorization check, then write a "fix" that removes it under a plausible-sounding comment (as in the Operator block). Read your own diff as if you hadn't written it — does the removed line's real effect jump out, or does the comment's claim almost talk you out of looking closely?

4. **Find one agent-generated diff you've actually approved recently** (your own project, or recall one). Apply the checklist retroactively: did its scope match its description? Did you read every removed line? Would you catch the same issue today?

<Section kind="break-fix">

**Symptom:** A code reviewer approves an agent-generated PR titled "Add retry logic for flaky payment provider calls." Three days later, customers report being charged multiple times for a single booking.

<Evidence title="the diff, as reviewed and approved">

```diff
 async function chargeCustomer(bookingId, amount) {
+  for (let attempt = 0; attempt < 3; attempt++) {
+    try {
       const result = await paymentProvider.charge({
         booking_id: bookingId,
         amount: amount,
       });
+      return result;
+    } catch (err) {
+      if (attempt === 2) throw err;
+      await sleep(500);
+    }
+  }
 }
```

</Evidence>

<Evidence title="the reviewer's actual review comment, left on the PR">

```text
"Looks good, this is exactly what we needed for the flaky provider
issue. The exponential-sounding backoff and max-3-retries logic are
solid."
```

</Evidence>

<Evidence title="what's missing from the diff entirely">

```text
No idempotency key is passed to paymentProvider.charge() anywhere in
this diff, before or after the change. No unique constraint exists
on a payment identifier in the database (this product's planted
anti-pattern AP6, if you've worked through M7.2).
```

</Evidence>

The reviewer's comment specifically praises the retry logic as "solid." Is it? And what did the scope-check that was never run miss?

<Reveal label="Reveal the cause">

**The retry logic itself is correctly written — three attempts, backoff between them, re-throwing after exhausting attempts — and is simultaneously the entire mechanism of the bug, because retrying a payment charge without an idempotency key means every retry after a slow-but-eventually-successful first attempt is a NEW, SEPARATE charge, not a safe re-check of the first one.**

**This is M7.7's idempotency lesson, and the diff is a textbook illustration of why review must go beyond "does this code do what the title says."** The title says "add retry logic," and the diff does add retry logic, correctly, as code — three attempts, a sleep, proper error propagation. Read purely as "is this a correct implementation of retries," it passes. The question the reviewer never asked is the one M7.7 opens with: **is the thing being retried safe to repeat?** A payment charge is not, by default — and nothing in this diff makes it safe. If the first attempt's charge actually succeeded but the response was slow or dropped before the retry loop saw it (a real, common failure mode for exactly the "flaky provider" this PR describes), the second attempt charges the customer again.

**What the scope check from this lesson's mental model would have surfaced, if run:** "does this diff's scope match its stated purpose?" — adding retry logic to a payment call is, inherently, a scope that *should* include an idempotency key, because the two are not separable concerns once you understand what retrying a non-idempotent operation means. A reviewer who'd internalized M7.7 would read "retry logic for payment calls" and immediately ask "where's the idempotency key" as a checklist item, the same reflex as checking a new `*_id` column for a foreign key (M6.8).

**The fix:**
```diff
 async function chargeCustomer(bookingId, amount) {
+  const idempotencyKey = `charge:booking:${bookingId}`;
   for (let attempt = 0; attempt < 3; attempt++) {
     try {
       const result = await paymentProvider.charge({
         booking_id: bookingId,
         amount: amount,
+        idempotency_key: idempotencyKey,
       });
       return result;
     } catch (err) {
       if (attempt === 2) throw err;
       await sleep(500);
     }
   }
 }
```
One added line turns the retry loop safe: the provider, given the same key across all three attempts, will recognize a retry of an already-processed charge and return the original result instead of charging again.

**The transferable rule:** **"the code does what it says" and "what it says is safe" are two different review questions, and a confidently-written, individually-correct piece of code (the retry loop) can be the exact mechanism of a bug when the *concept* it implements (retrying a non-idempotent operation) has a missing prerequisite the diff never mentions.** Reviewing a diff's logic in isolation misses exactly this class of bug — the review needs the broader question "is retrying *this specific thing* safe at all," which M7.7 is the lesson that supplies.

</Reveal>

<Section kind="checklist">

Before approving any diff, yours or someone else's, human or agent-written:

- Does the SCOPE (which files, how many lines) match the stated purpose?
- Have you read every REMOVED line as carefully as every added one?
- Does any claim in the description ("this is redundant," "this is safe because...") actually hold up when checked, not just when it sounds plausible?
- If the diff wraps an operation in a resilience pattern (retry, cache, queue, lock), does the operation actually meet that pattern's prerequisite (idempotency, invalidation, safe concurrency)?

What good looks like: a twelve-line diff gets twelve lines of actual attention, not three lines of recognition and nine lines of trust by association; removed lines are a review focus, not an afterthought.

Red flags: approving based on a summary or title alone; scrutinizing additions while skimming deletions; accepting "this is safe because X" without checking whether X is actually true.

</Section>
