<Section kind="story">

A deploy went out at 2pm with a subtle bug in the checkout flow. By 2:15, support tickets were arriving. The on-call engineer spent the next forty minutes **debugging the bug** — reading the diff, reproducing it locally, forming a theory, writing a fix, testing the fix — while checkout stayed broken for every real customer the entire time.

The fix, once found, was three lines. The forty minutes of debugging happened entirely *before* rolling back, because nobody had made rolling back the reflexive first move — it felt like "giving up" on understanding the problem, or like it would somehow make the problem harder to diagnose afterward. Neither is true: the previous version was working an hour earlier, reverting to it takes roughly as long as the original deploy did, and *none* of the forty minutes of live debugging needed to happen while customers were affected — it could have happened just as effectively against the now-restored, working production, with the broken version sitting safely in a branch for exactly as long as the investigation required.

The three-line fix was correct. The decision to debug live, for forty minutes, before restoring service, was the actual incident.

</Section>

<Section kind="already-did">

You've had a deploy go wrong and felt the pull to understand it before doing anything else — it's a completely natural instinct, and it's backwards for almost every production incident. M14.2 will give you the full incident-response version of this; this lesson is the git-and-deploy mechanics underneath it, including the part most people learn the hard way: not everything that goes out in a deploy *can* actually be rolled back, no matter how fast you click the button.

</Section>

<Section kind="mental-model">

### Rollback first, debug second — and why that ordering is correct, not just faster

<Callout type="key">
**Rolling back restores service without requiring you to understand the cause first.** Debugging *while broken* costs every minute of that debugging to your actual users; debugging *after* restoring service costs nothing extra to them — the investigation takes exactly as long either way, but only one ordering has customers suffering through it. This is the entire argument, and it holds regardless of how confident you feel that you'll find the fix quickly — you often won't be as fast as you expect, and the story's forty minutes is the typical case, not the exception.
</Callout>

### What's actually reversible, and what fundamentally isn't

  <text x="12" y="140" className="sub">Rolling back CODE while a migration has already run means the OLD code is now running</text>
  <text x="12" y="162" className="sub">against the NEW schema — which may be exactly the wrong combination, not automatically safer.</text>
  <text x="12" y="192" className="sub">This is why M6.3 insists migrations are forward-only in practice: "rollback" means something</text>
  <text x="12" y="214" className="sub">different and much harder for data than it means for code.</text>

**Code** is symmetric: the previous version was a known-good artifact, and redeploying it is exactly as safe as that version already was. **Database schema changes** are not: if a migration has already run and new rows have been written under the new schema, rolling back the *code* to a version that expects the *old* schema doesn't undo the migration — it creates a mismatch, potentially a worse one than the original bug. **Anything with an external side effect** — a sent email, a captured payment, a published webhook — cannot be rolled back by any deploy mechanism at all; it already happened in the world, and "rollback" there means a *new*, separate action (a refund, a correction email), not an undo.

### How rollback actually works, per platform

| Platform | Mechanism |
|---|---|
| Vercel/Render/similar | "Redeploy" or "promote" a previous build — usually seconds, because the artifact already exists |
| Raw Docker/VPS | Re-run the deploy with the previous image tag |
| This project's demo app | `git revert`, then rebuild (verified below) |
| Kubernetes | Roll back to the previous ReplicaSet/revision |

The universal mechanism underneath all of them: **the previous version's build artifact already exists somewhere, and rollback is "point traffic at that instead" — which is fast precisely because nothing needs to be rebuilt from scratch.** This is also why keeping a few recent build artifacts around (most platforms do this automatically) matters — a rollback that requires rebuilding from an old commit is slower and riskier than one that just re-promotes an artifact that's already sitting there.

<Section kind="tools">

| Need | Tool |
|---|---|
| Code rollback | Your platform's redeploy/promote feature, or `git revert` + redeploy |
| See what's different between current and previous | `git diff <previous-tag> <current-tag>` before deciding what a rollback would actually change |
| Avoid migration-vs-code rollback mismatches | M6.3's expand/contract pattern — designed specifically so a code rollback is always safe regardless of migration state |
| Feature-level rollback without a deploy | A feature flag (M2.5) — flip it off instead of redeploying at all |

What good looks like: rollback is the reflexive first response to "something just broke after a deploy," not a last resort reached for after debugging fails; and the team knows, for their actual migration practices, whether a code rollback is always safe or sometimes isn't.

<Section kind="break-fix">

**Symptom:** A deploy causes a visible bug. The on-call engineer rolls back the code immediately — the platform confirms the previous version is live within 30 seconds. The bug *persists* anyway, identically, even though the "old" code is now running.

<Evidence title="the deploy that caused the bug">

```text
Deploy included:
  1. A migration: ALTER TABLE products ADD COLUMN display_price_cents integer;
     + a backfill: UPDATE products SET display_price_cents = price * 100;
  2. New code: reads product.display_price_cents, no longer reads product.price
```

</Evidence>

<Evidence title="what rollback actually did">

```text
$ git log --oneline -2
a1b2c3d (rolled back TO this)  previous: reads product.price
e4f5678 (rolled back FROM this) new: reads product.display_price_cents

Rollback completed: previous code (a1b2c3d) is now deployed and running.

$ SELECT price, display_price_cents FROM products LIMIT 3;
 price | display_price_cents
-------+---------------------
 19.99 |                 1999
 24.50 |                 2450
 (migration already ran — this data is fine)
```

</Evidence>

<Evidence title="the actual bug, still present after rollback">

```text
Products page still shows: "Price: $0.00" for every product
```

</Evidence>

The old code is confirmed running. The migration's data looks correct. Why does the bug persist?

<Reveal label="Reveal the cause">

**The rollback restored the OLD code, which reads `product.price` — but the actual bug was never in the new code's column choice; it was somewhere else entirely (the real cause is deliberately not shown here, because the point of this break-fix is what the evidence should make you question, not a single specific root cause), and the rollback's success at restoring old code doesn't guarantee old code was ever the problem to begin with.**

Re-read what actually happened: rollback restored `a1b2c3d`, which reads `product.price`. The `price` column was never touched by the migration — it's still there, unchanged, holding `19.99`, `24.50`, and so on. If the bug persists with the old code reading an unchanged column holding correct values, **the bug is not, and was never, a code-version problem at all.** Something else — a cache serving a stale or corrupted value (M6.5), a separate service that computes displayed price independently, or a frontend build that didn't actually get rolled back alongside the backend — is the real cause, and rolling back the backend code addressed a hypothesis that the evidence doesn't actually support once you check it carefully.

**The transferable lesson, which matters more than any single specific cause here:** **a rollback "working" (the platform confirms the old version is live) and a rollback "fixing the symptom" are different claims, and conflating them wastes exactly the time rollback was supposed to save.** If you roll back and the bug persists, the correct next move is not "roll back further" or "the rollback must have failed somehow" — it's **recognizing that the deploy you rolled back might not have been the actual cause**, and now you need the debugging method (M8.6) to find out what *is*, with the one advantage that you're no longer debugging live — you've already restored a confirmed-old, confirmed-working-before code version, so whatever is still broken is broken independent of this specific deploy, and the investigation can proceed calmly.

**What this specific evidence actually rules in, worth practicing the reasoning on:** check the cache (M6.5) first — a cached "price" computed before the migration even started, with a TTL long enough to still be serving stale data, would produce exactly this symptom regardless of which code version is running, because neither code version ever gets a chance to compute a fresh value while the cache is being served. That's the layer-isolation habit from M8.6, applied to a deploy-rollback scenario instead of a live-incident one.

</Reveal>

</Section>

<Section kind="checklist">

When something breaks right after a deploy:

- Has rollback happened FIRST, before any live debugging? If not, why not — is there a specific, deliberate reason, or is it just not the reflexive first move yet?
- Once rolled back: is the previous version ACTUALLY confirmed running (checked directly), separate from trusting a platform's success message?
- Does the bug persist after a confirmed rollback? If so, stop assuming the rollback failed — consider that this deploy might never have been the actual cause.

For any deploy that includes a migration:

- If we needed to roll back the code only, immediately, would the old code still work against the new schema? (M6.3's expand/contract pattern is what makes this always "yes.")

What good looks like: rollback is the reflexive first response, taking roughly as long as the original deploy; the team can state clearly which of their changes are cleanly reversible (code) and which aren't (migrations, sent side effects) before an incident, not during one.

Red flags: debugging live, for an extended period, before restoring service; assuming a rollback that didn't fix the symptom means the rollback failed, rather than questioning whether the deploy was the actual cause; a migration shipped in the same deploy as code that depends on it, with no plan for a code-only rollback.

</Section>
