<Section kind="story">

A founder tested her booking flow about two hundred times before launch. She tried every edge case she could imagine: invalid dates, missing fields, a room that didn't exist, double-clicking the submit button. Everything behaved.

Launch day. Eleven minutes in, two customers booked the same studio for the same evening. Then a third pair did it. Her inventory of available slots went negative. A customer's payment succeeded while their booking row didn't exist.

She had tested every path through her code. What she had never tested was **two people arriving at the same instant**, because every test she wrote ran one request at a time, in order, alone. Her code was correct for the only situation it had ever been in: a world with one user.

Production is never that world. And the failures that only appear with two users don't throw errors — they produce wrong data, silently, while every log line says 200.

</Section>

<Section kind="already-did">

You have already hit concurrency without naming it. A double-clicked submit button creating two records. A webhook that fired twice. A test that passes alone and fails in CI when the suite runs in parallel. A "works on my machine" bug that only appeared under real traffic.

You've also been protected from it by accident. If your app has one user at a time — you, in development — requests queue up neatly and every read-then-write sequence completes undisturbed. **Development is a concurrency-free environment,** which is precisely why these bugs ship.

And if you've followed an agent's instructions to "add a transaction" or "use `FOR UPDATE`", you've applied a concurrency fix without necessarily knowing what it was defending against. This module makes that explicit.

</Section>

### What a server is actually doing

Your app does not handle one request at a time. While request A waits for the database (milliseconds of doing nothing), the process picks up request B. Requests **interleave**.

**The analogy.** Two people editing the same paper form. Each photocopies it, writes a line, and files their copy back. Whoever files second wins; the other line never existed. Neither person did anything wrong, and nobody is told.

### Three places concurrency comes from

Even with *one* server process, you have concurrency. But it arrives from three directions, and knowing which applies to you matters:

| Source | When | Shares memory? |
|---|---|---|
| **Interleaved requests in one process** | Always, from your second simultaneous user | Yes — module state is shared |
| **Multiple instances / replicas** | Scaling out, or any PaaS with >1 instance | **No** — separate memory, same database |
| **Background workers and crons** | A worker, a scheduled job, a webhook handler | No — separate process, same database |

<Callout type="key">
The thing all three share is **the database**. That's why the database is where concurrency problems get *solved* — it's the only component that all concurrent actors can see. An in-process lock protects you from source 1 and does nothing about sources 2 and 3, which is why in-memory solutions are a trap (M1.1's module-scope problem, met again from the other side).
</Callout>

### The two dangerous shapes

Almost every concurrency bug in a web app is one of these two patterns. Learn to recognise them in code.

**1. <Term k="read-modify-write">Read-modify-write</Term>** — read a value, change it in your code, write it back:

```ts
const booking = await db.query("SELECT notes FROM bookings WHERE id=$1", [id]);
const notes = booking.notes;            // ← read
notes.push(newNote);                    // ← modify (in your process)
await db.query("UPDATE bookings SET notes=$1 WHERE id=$2", [notes, id]);  // ← write
```

Two requests both read the old value; the second write erases the first. Result: a <Term k="lost-update">lost update</Term>.

**2. <Term k="check-then-act">Check-then-act</Term>** — verify something is allowed, then do it:

```ts
const clashes = await db.query("SELECT id FROM bookings WHERE room_id=$1 AND ...");
if (clashes.length > 0) return conflict();   // ← check
await db.query("INSERT INTO bookings ...");  // ← act
```

Two requests both check, both find the slot free, both insert. Result: a double booking.

**The tell in both cases is a gap between two database calls where your code holds a decision based on data that can go stale.** Anything that makes the gap wider — an `await` on a third-party API, a slow query, a `fraudCheck()` — widens the window. The demo app's booking endpoint has a 150ms fraud check sitting in exactly that gap, which is why its race is so easy to hit.

### Why your tests don't catch it

| Test style | Catches concurrency bugs? |
|---|---|
| Unit tests | No — one call at a time by construction |
| Integration tests | No — sequential requests |
| Manual QA | Almost never — you can't click fast enough |
| **Concurrent load test** | **Yes** — N simultaneous identical requests |

That last row is a test you can write in ten lines, and almost nobody does. `Promise.all` with fifteen identical requests is the entire technique, and it's what `scripts/load/booking-rush.js` does.

<Operator>

Demonstrate interleaving yourself, then measure its consequences.

```bash
cd demo-app

# ── Prove requests overlap in time (not queued) ───────────────────────
#   Sequential: 5 requests, one after another
time (for i in 1 2 3 4 5; do curl -s -o /dev/null localhost:3001/api/bookings; done)
#   Concurrent: the same 5 at once
time (for i in 1 2 3 4 5; do curl -s -o /dev/null localhost:3001/api/bookings & done; wait)
#   Concurrent total ≈ the slowest single request, not the sum. They overlapped.

# ── See several requests in flight inside the database ───────────────
(for i in $(seq 1 20); do curl -s -o /dev/null localhost:3001/api/bookings & done) >/dev/null 2>&1
docker compose exec -T db psql -U ots -d demo -c "
  SELECT count(*) AS in_flight, state FROM pg_stat_activity
   WHERE datname='demo' GROUP BY state;"

# ── One process, many requests: confirm the shape (M1.1) ─────────────
docker compose exec app sh -c 'ps -o pid,comm -e | grep -c "[n]ode"'
#   One PID serving everything ⇒ module-level state is SHARED between
#   all those interleaved requests.

# ── The ten-line concurrency test you should own ─────────────────────
cat > /tmp/concurrent-test.mjs <<'EOF'
const APP = "http://localhost:3001";
const N = 15;
const body = { room_id: 4, customer_name: "concurrency-probe",
               date: "2026-12-20", start_hour: 14, end_hour: 16 };
const results = await Promise.all(
  Array.from({ length: N }, () =>
    fetch(`${APP}/api/bookings`, {
      method: "POST", headers: { "Content-Type": "application/json" },
      body: JSON.stringify(body),
    }).then(r => r.status))
);
const created = results.filter(s => s === 201).length;
console.log(`statuses: ${results.join(",")}`);
console.log(created === 1 ? "PASS: exactly one won" : `FAIL: ${created} of ${N} succeeded`);
EOF
node /tmp/concurrent-test.mjs

# ── Clean up probe rows so the demo data stays sensible ──────────────
docker compose exec -T db psql -U ots -d demo -c \
  "DELETE FROM bookings WHERE customer_name='concurrency-probe';"
```

That test is the thing to steal. Any endpoint that must happen "at most once" — booking, charging, claiming, redeeming — deserves fifteen simultaneous identical requests in CI, asserting that exactly one succeeded.

</Operator>

<Section kind="tools">

You don't need special tooling to find these bugs — you need to *generate concurrency*, which is a few lines in anything.

| Tool | Use | Note |
|---|---|---|
| `Promise.all` in a script | Hitting one endpoint N times simultaneously | The ten-line test above; start here |
| `xargs -P` / `&` + `wait` in bash | Same, from a shell | `seq 20 \| xargs -P20 -I{} curl -s …` |
| **`oha`, `hey`, `vegeta`** | Sustained load with concurrency control | `oha -n 200 -c 20 URL` — good for latency under load |
| `k6` | Scripted scenarios, assertions, CI | Worth it when load testing becomes routine |
| `pgbench -c` | Concurrency against Postgres directly | Isolates database-level behaviour from app code |
| Two `psql` sessions side by side | Watching locks and transactions interact | The best *teaching* tool there is (L7.4) |

What good looks like: every endpoint with an "at most once" or "exactly N available" rule has a concurrent test asserting the invariant, running in CI. Not a load test for performance — a **correctness** test with concurrency.

The mental shift worth making: concurrency bugs aren't performance problems, they're **correctness** problems. They belong with your tests, not with your monitoring, because monitoring will never tell you about them (nothing errors).

</Section>

<Section kind="break-fix">

**Symptom:** A team added per-user rate limiting to their signup endpoint — five attempts per minute. It tested perfectly. In production, a bot comfortably made forty signups a minute, and legitimate users occasionally got rate-limited after only two attempts.

<Evidence title="the implementation">

```ts
// lib/rate-limit.ts
const attempts = new Map<string, number[]>();        // ip → timestamps

export function allow(ip: string, limit = 5, windowMs = 60_000): boolean {
  const now = Date.now();
  const recent = (attempts.get(ip) ?? []).filter(t => now - t < windowMs);
  if (recent.length >= limit) return false;
  recent.push(now);
  attempts.set(ip, recent);
  return true;
}
```

</Evidence>

<Evidence title="production facts">

```text
Platform: Render, web service, autoscaling 2–6 instances
Current instances: 4
Logs (bot IP 203.0.113.88, one minute):
  instance-a: signup.attempt ip=203.0.113.88 (5 allowed, then blocked)
  instance-b: signup.attempt ip=203.0.113.88 (5 allowed, then blocked)
  instance-c: signup.attempt ip=203.0.113.88 (5 allowed, then blocked)
  instance-d: signup.attempt ip=203.0.113.88 (5 allowed, then blocked)
  → 20 signups from one IP in a minute, each instance believing it blocked at 5

Legitimate user complaints: "it says too many attempts and I only tried twice"
Load balancer: no session affinity (requests distributed round-robin)
```

</Evidence>

Two opposite symptoms — too permissive for the bot, too strict for users — from one cause. Name it.

<Reveal label="Reveal the cause">

**The rate limiter's state lives in each instance's process memory, so there are four independent limiters instead of one shared one.**

**Why the bot got 20 signups:** each of the four instances has its own `Map`. The bot's requests are distributed round-robin, so each instance sees roughly a quarter of them and allows 5 before blocking. The effective limit is `limit × instances` — and because the platform autoscales from 2 to 6, the *real* limit silently varies with traffic. Under heavy load it scales up and the limit gets *looser* precisely when you need it tighter.

**Why legitimate users were blocked after two attempts:** the opposite face of the same bug. A user's three earlier attempts landed on instance-a. Their fourth lands on instance-b, which has no record… but a user who retries several times can also land repeatedly on *one* instance whose `Map` already holds entries from a previous burst — and there's a second defect making this worse: `attempts` is **never cleaned up for inactive IPs**. The map only filters when an IP is seen again, so memory grows unbounded (M1.6's leak) and stale state persists per instance. Users experience the limiter as random, because which instance answers is random.

**Map it onto the mental model.** This is concurrency source 2 — multiple instances with separate memory. The limiter is correct for source 1 (interleaved requests in one process) and useless for sources 2 and 3. And there's a read-modify-write race *within* each instance too: two simultaneous requests both read `recent`, both find it under the limit, both push. On a single instance the limit is already soft.

**The fix: shared state, and make the check atomic.** The limiter must live where every actor can see it — Redis, which the app already has:

```ts
// Atomic: INCR and EXPIRE in one round trip, correct across all instances.
const key = `rl:signup:${ip}:${Math.floor(Date.now() / 60_000)}`;
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, 120);
if (count > 5) return tooManyRequests();
```

`INCR` is a single atomic operation — no read-modify-write gap, no per-instance divergence, and the key expires itself so nothing leaks. (A sliding window via a sorted set is more precise; a fixed bucket like this is usually enough and far simpler.)

**Two general rules this establishes:**
1. **Any counter, limiter, lock or session shared between users must live outside the process** — Redis or the database. In-process is correct only for things genuinely local to one instance (a connection pool, a prepared-statement cache).
2. **Prefer an operation the store performs atomically** (`INCR`, `UPDATE … SET n = n + 1`, a unique constraint) over reading a value into your code and writing it back. The gap in read-modify-write is where the bug lives, and the way to be safe is to not have a gap.

**And the deeper point for this module:** if you'd been asked "is this rate limiter correct?", reading the function alone would tell you yes. It's only wrong in the presence of concurrency and multiple instances — context that doesn't appear in the code. That's why these bugs survive code review, your tests, and your agent.

</Reveal>

<Section kind="checklist">

Questions to ask about any endpoint that changes data:

- Does it read a value, decide, then write? (Read-modify-write.)
- Does it check whether something is allowed, then do it? (Check-then-act.)
- What sits in the gap between those two database calls? Does anything `await` there?
- What happens if two requests execute this simultaneously? Write down the end state.
- Is there any shared counter, limit or lock in process memory?
- How many instances does this run on in production? (If more than one, in-process state is already wrong.)
- Is there a test that fires N simultaneous identical requests and asserts the invariant?

What good looks like: every "at most once" rule has a concurrent correctness test in CI; shared state lives in Redis or the database; counters use atomic operations rather than read-modify-write.

Red flags: a rate limiter, counter, or session store in a module-level variable; "it works, I tested it" about an endpoint never tested concurrently; concurrency treated as a performance topic rather than a correctness one.

</Section>
