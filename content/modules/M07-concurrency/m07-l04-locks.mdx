<Section kind="story">

Tuesday, 11:04. A developer runs a migration to add a column to the `bookings` table. It's a tiny change — a nullable text column, no data rewrite, instant in staging.

11:05: the site stops responding. Every page. Not slow — *hung*. No errors in the application logs, no CPU on the database, no errors anywhere. Just silence, and a spinner.

11:19: he cancels the migration. The site recovers instantly, as if nothing happened.

What occurred: an analytics query someone had opened in a SQL console at 10:52 was still running — a `SELECT` over the whole bookings table, holding a read lock. The migration's `ALTER TABLE` needed an exclusive lock, so it waited. And because Postgres queues lock requests **in order**, every subsequent query touching `bookings` queued *behind the migration*. One idle analytics tab, one small migration, and the entire product was down for fifteen minutes.

The database was healthy throughout. It was doing exactly what it promised. The failure was in not knowing that **a waiting lock blocks everyone behind it.**

</Section>

<Section kind="already-did">

You've been locked and not known it. A query that usually takes 20ms occasionally taking 4 seconds. A migration that "hung" and that you cancelled and re-ran successfully later. A deploy that timed out and worked on the second attempt. Those are lock waits.

If you've ever followed an agent's advice to add `SELECT … FOR UPDATE` to fix a race, you've used a lock deliberately. If you've seen `deadlock detected` in a log, Postgres has already saved you from one — by killing one of your transactions.

The thing nobody tells you is that locks are mostly **invisible**: a blocked query produces no error, no log line, and no CPU usage. It just waits. Which is why "everything is slow and nothing is wrong" is the characteristic signature.

</Section>

<Section kind="mental-model">

### What a lock is

A <Term k="row-lock">lock</Term> is a claim on something — a row, a table — held **until the transaction ends**. That last clause is the whole subject: lock duration equals transaction duration, so every rule about short transactions (L7.3) is really a rule about locks.

Postgres takes locks for you automatically:

| You run | Lock taken | Blocks |
|---|---|---|
| `SELECT` | Nothing on rows; a weak table lock | Only `ALTER`/`DROP` |
| `UPDATE` / `DELETE` | Exclusive **row** lock on affected rows | Other writes to *those rows* |
| `INSERT` | Row lock on the new row | Conflicting unique/exclusion keys |
| `SELECT … FOR UPDATE` | Exclusive row lock, deliberately | Other writers and `FOR UPDATE` readers |
| `ALTER TABLE` | `ACCESS EXCLUSIVE` on the **whole table** | **Everything, including `SELECT`** |
| `CREATE INDEX` (without `CONCURRENTLY`) | Blocks writes on the table | All `INSERT`/`UPDATE`/`DELETE` |

<Callout type="warn">
**The queue is the dangerous part.** Postgres grants lock requests roughly in order. If a long `SELECT` holds a weak lock and an `ALTER TABLE` queues behind it waiting for an exclusive lock, then every *new* query — even a fast `SELECT` — queues behind the `ALTER`. One slow query plus one DDL statement takes down everything touching that table. This is why the story's site died from a *nullable column addition*.
</Callout>

### Using locks on purpose: `SELECT … FOR UPDATE`

When an invariant spans multiple rows and a constraint can't express it, lock the rows you're about to depend on:

```sql
BEGIN;
  -- Claim the row. A second transaction doing this WAITS here.
  SELECT seats_left FROM events WHERE id = $1 FOR UPDATE;
  -- Now the value cannot change under us.
  UPDATE events SET seats_left = seats_left - 1 WHERE id = $1;
COMMIT;                 -- lock released
```

This converts a race into a queue: correct, at the cost of throughput. Two variants matter:

- **`FOR UPDATE NOWAIT`** — fail immediately instead of waiting. Good for "tell the user it's busy" rather than hanging.
- **`FOR UPDATE SKIP LOCKED`** — ignore locked rows. This is what turns a table into a work queue (L7.9):

```sql
-- Two workers run this simultaneously and claim DIFFERENT rows, no waiting.
BEGIN;
  SELECT id FROM jobs WHERE status='pending'
   ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;
  -- …process them…
COMMIT;
```

### Deadlocks

Two transactions each holding a lock the other needs. Neither can proceed, so Postgres detects the cycle (after ~1s) and **kills one**:

```text
ERROR:  deadlock detected
DETAIL: Process 541 waits for ShareLock on transaction 892; blocked by process 548.
        Process 548 waits for ShareLock on transaction 889; blocked by process 541.
```

The classic cause is **inconsistent lock ordering**: one code path updates booking 1 then booking 2, another updates 2 then 1. The fix is cultural and simple — always acquire locks in a deterministic order (`ORDER BY id`), and retry the victim (`40P01`, same handler as serialization failures from L7.3).

### Reading lock waits: the three diagnostic queries

A blocked query is silent, so you need to go looking. These three answer "who is stuck, and who is to blame":

```sql
-- 1. Who is waiting, and who is blocking them?
SELECT pid, wait_event_type, wait_event, pg_blocking_pids(pid) AS blocked_by,
       now() - query_start AS waiting_for, left(query, 60) AS query
  FROM pg_stat_activity
 WHERE wait_event_type = 'Lock';

-- 2. Who is holding a transaction open (the usual culprit)?
SELECT pid, state, now() - xact_start AS open_for, left(query, 60)
  FROM pg_stat_activity
 WHERE xact_start IS NOT NULL AND now() - xact_start > interval '5 seconds'
 ORDER BY xact_start;

-- 3. Unblock, when you must (last resort, in order of violence)
SELECT pg_cancel_backend(<pid>);      -- cancel the query, keep the connection
SELECT pg_terminate_backend(<pid>);   -- kill the connection entirely
```

`pg_blocking_pids` is the single most useful function in this lesson: it names the blocker directly, turning "everything is slow" into "PID 541 has held a transaction open for nine minutes".

### Migrations: the special case

DDL takes `ACCESS EXCLUSIVE`, which blocks everything. Two habits make migrations safe:

```sql
-- Fail fast rather than queue up behind a long query and block the world.
SET lock_timeout = '3s';
ALTER TABLE bookings ADD COLUMN notes_v2 jsonb;

-- Build indexes without blocking writes (cannot run inside a transaction).
CREATE INDEX CONCURRENTLY idx_bookings_date ON bookings (date);
```

`lock_timeout` is the lesson of the story in one line: if the lock isn't available in 3 seconds, the migration fails and you retry later — instead of taking the site down for fifteen minutes.

<Section kind="tools">

| Need | Tool |
|---|---|
| Who is blocked, by whom | `pg_blocking_pids(pid)` in `pg_stat_activity` |
| What locks exist | `pg_locks` joined to `pg_stat_activity` |
| Long-open transactions | `pg_stat_activity.xact_start` |
| Stop a blocker | `pg_cancel_backend` → `pg_terminate_backend` |
| Prevent migration disasters | `SET lock_timeout`, `CREATE INDEX CONCURRENTLY` |
| Prevent stuck transactions | `idle_in_transaction_session_timeout` |
| Safer migration tooling | `pgroll`, `reshape`, Strong Migrations (Rails), Prisma/Drizzle with manual review |
| Monitoring | Alert on `wait_event_type='Lock'` count > 0 for more than N seconds |

Settings worth having before you need them:

```sql
ALTER DATABASE demo SET idle_in_transaction_session_timeout = '30s';
ALTER DATABASE demo SET lock_timeout = '5s';          -- app sessions fail fast
ALTER DATABASE demo SET deadlock_timeout = '1s';      -- detection interval (default)
ALTER DATABASE demo SET log_lock_waits = on;          -- log waits > deadlock_timeout
```

`log_lock_waits = on` is the one people miss: it turns invisible lock waits into log lines you can search afterwards, which is the difference between diagnosing the story's outage and guessing at it.

What good looks like: migrations run with `lock_timeout`; indexes are built `CONCURRENTLY`; code locks rows in a consistent order; deadlock and serialization errors are retried; and something alerts when a query waits on a lock for more than a few seconds.

<Section kind="hands-on">

```bash
cd demo-app && docker compose up -d --build
```

1. **Watch a lock block a writer** (Operator block 1). Note the ~5 second wait and that *nothing errored* — the second query just took five seconds.

2. **Diagnose a live block** (block 2). This is the skill: run the `pg_blocking_pids` query while something is blocked and read `blocked_by`. Practise it until it's muscle memory — it's the first query to run when anyone says the site is hanging.

3. **Cause a deadlock and read the error** (block 4). Note which session died and that the other committed normally. Postgres chose a victim; your code's job is to retry it.

4. **Use `SKIP LOCKED`** (block 5) and confirm the two workers claimed *disjoint* rows without waiting. You'll build on this in L7.9.

5. **Reproduce the story's outage shape.** Hold a long transaction on `bookings`, queue a migration behind it, then send a normal read. Run all three in the background so you can inspect the queue *while* it exists — if you time the read in the foreground instead, it completes before you can look and the evidence is gone:
   ```bash
   # 1. the holder: a long transaction that read bookings
   (docker compose exec -T db psql -U ots -d demo -c \
     "BEGIN; SELECT count(*) FROM bookings; SELECT pg_sleep(14); COMMIT;" >/dev/null 2>&1 &)
   sleep 1
   # 2. the migration, which must wait for an exclusive lock
   (docker compose exec -T db psql -U ots -d demo -c \
     "ALTER TABLE bookings ADD COLUMN blocked_demo text;" >/dev/null 2>&1 &)
   sleep 1
   # 3. an ordinary read, which should be instant
   (docker compose exec -T db psql -U ots -d demo -c \
     "SELECT count(*) FROM bookings;" >/dev/null 2>&1 &)
   sleep 3
   docker compose exec -T db psql -U ots -d demo -c "
     SELECT pid, wait_event, pg_blocking_pids(pid) AS blocked_by, left(query,42) AS q
       FROM pg_stat_activity WHERE wait_event_type='Lock' ORDER BY query_start;"
   ```
   Expected output — read the `blocked_by` column carefully:
   ```text
    pid  | wait_event | blocked_by |                     q
   ------+------------+------------+--------------------------------------------
    2653 | relation   | {2646}     | ALTER TABLE bookings ADD COLUMN blocked_de
    2660 | relation   | {2653}     | SELECT count(*) FROM bookings;
   ```
   The migration waits for the long transaction — and the plain `SELECT` waits for **the migration**, not for the original holder. That second row is the queue, and it's why one DDL statement takes down everything. (Timed in the foreground, that `SELECT` takes ~9 seconds instead of ~2ms.) Wait for it to drain before continuing.

6. **Fix it with `lock_timeout`.** Wait for everything to finish, then repeat step 5 with `SET lock_timeout='2s';` before the `ALTER`. The migration now fails in 2 seconds and the site keeps serving. Clean up:
   ```bash
   docker compose exec -T db psql -U ots -d demo -c "ALTER TABLE bookings DROP COLUMN IF EXISTS blocked_demo;"
   ```

7. **Turn on lock-wait logging** and confirm waits appear in the database logs:
   ```bash
   docker compose exec -T db psql -U ots -d demo -c "ALTER DATABASE demo SET log_lock_waits = on;"
   docker compose logs --since 5m db | grep -i "lock" | tail -5
   ```

Three parties, one outage. Explain the chain precisely, and give both the immediate and permanent fixes.

<Reveal label="Reveal the cause">

**A lock queue: an idle analytics transaction blocks a migration, and the migration blocks all 47 normal queries behind it.**

**The chain, in order:**

1. **08:55 — the analytics tool** opens a transaction, runs its dashboard query against `bookings`, and then sits `idle in transaction` without committing. It holds a weak `ACCESS SHARE` lock on `bookings` — harmless on its own, and it would coexist happily with all normal traffic forever.
2. **09:00 — the migration** runs `ALTER TABLE bookings ADD COLUMN`, which needs `ACCESS EXCLUSIVE`. That conflicts with the analytics session's lock, so the migration **waits** (pid 8812, `blocked_by {8790}`).
3. **09:00 onwards — every other query** touching `bookings` now queues *behind the waiting migration*, because Postgres grants locks roughly in request order and will not let later weak-lock requests jump ahead of a pending exclusive request. Note the `blocked_by` column: pids 8814, 8815, 8816 are blocked by **8812 (the migration)**, not by 8790. Forty-seven queries, all waiting on a migration that is itself waiting.
4. The app hangs. Requests climb to the 30s proxy timeout. Nothing errors in the database because waiting is not an error.

**Why every signal looked healthy:** CPU and memory are flat because waiting consumes neither. The health check passes because `SELECT 1` doesn't touch `bookings`. There are no application errors because the queries haven't failed — they haven't finished. This is the characteristic signature of lock contention, and it's why `pg_blocking_pids` is the diagnostic that matters: it's the only one that shows the structure.

**The three-minute duration is the coincidence that made it survivable** — the analytics transaction eventually ended, the migration acquired its lock and completed in milliseconds, and the queue drained. Had the analytics tool held its transaction for an hour, so would the outage.

**Immediate fix (during an incident):**
```sql
SELECT pg_cancel_backend(8812);     -- cancel the waiting migration first:
                                    -- this drains the queue instantly
```
Cancel the **migration**, not the analytics session — it's the thing 47 queries are queued behind, and cancelling it is harmless (the migration simply didn't apply). Then deal with 8790.

**Permanent fixes, all three needed:**

1. **Every migration gets `lock_timeout`.** This is the single highest-value change:
   ```sql
   SET lock_timeout = '3s';
   ALTER TABLE bookings ADD COLUMN source text;
   ```
   The migration now fails after 3 seconds instead of parking an exclusive lock request in front of the world. A failed migration is a retry; a 3-minute outage is an incident.
2. **Stop the analytics tool holding transactions open.** Set `idle_in_transaction_session_timeout` (globally, or on the analytics role specifically), and configure the tool to use autocommit for read-only dashboards:
   ```sql
   ALTER ROLE analytics SET idle_in_transaction_session_timeout = '15s';
   ```
3. **Make it visible next time:** `ALTER DATABASE demo SET log_lock_waits = on;` and alert when any session has `wait_event_type='Lock'` for more than ~5 seconds. This outage was invisible to every existing signal for two weeks.

Worth adding: **don't run migrations in the same window as a known analytics refresh**, and consider reader access via a replica so dashboard queries can't interact with production DDL at all (M9.4).

**The transferable lesson:** lock problems are not about the lock *you* take — they're about the **queue**. A harmless reader plus a harmless DDL statement combined into a total outage, and neither party did anything individually wrong. `lock_timeout` on DDL is the seatbelt, and `pg_blocking_pids` is how you see the structure when it fails.

</Reveal>

<Section kind="checklist">

When something is "hanging" rather than erroring:

1. Run the `pg_blocking_pids` query. Who is waiting, and on whom?
2. Find sessions `idle in transaction` — that's usually the root holder.
3. Follow the chain: the thing blocking 47 queries may itself be blocked.
4. Cancel the blocker that is draining the queue (often a waiting DDL), then fix the root.

Standing protections:

- `lock_timeout` set on every migration — the single highest-value habit here.
- `CREATE INDEX CONCURRENTLY` for indexes on large tables.
- `idle_in_transaction_session_timeout` set, especially for analytics roles.
- `log_lock_waits = on`, so waits are searchable afterwards.
- Rows locked in a consistent order (`ORDER BY id`) wherever several are updated.
- Retry handling for `40P01` (deadlock) and `40001` (serialization).
- An alert on any session waiting on a lock for more than a few seconds.

What good looks like: migrations fail fast rather than blocking the world; lock waits are logged and alerted; deadlocks are rare and retried automatically.

Red flags: an analytics tool or BI dashboard connected to the primary with long transactions; migrations run without `lock_timeout`; "it hung, we re-ran it and it worked" as an accepted outcome.

</Section>
