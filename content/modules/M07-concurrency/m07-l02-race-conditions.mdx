<Section kind="story">

An events startup sold tickets to a 200-capacity venue. Their checkout counted sold tickets, compared against capacity, and inserted a row if there was room. It worked for months.

Then an artist posted the link to 80,000 followers at once.

They sold 247 tickets. Forty-seven people had valid confirmations for a venue that could not hold them. The fix cost them refunds, apology credits, and a day of support — but the part that stung was the postmortem, where an advisor asked what guaranteed capacity, and the honest answer was *"the code checks it"*.

Checking is not guaranteeing. A check is a statement about the past: *at the moment I looked, there were 199 tickets sold.* By the time the insert ran, that was no longer true. The only thing that can *guarantee* a rule about data is the database holding the data — and it has purpose-built machinery for exactly this, which they weren't using.

</Section>

<Section kind="already-did">

You have written the vulnerable shape. Everyone has, because it's the obvious way to express a rule:

```ts
const existing = await db.query("SELECT … WHERE …");   // is it taken?
if (existing.length > 0) return conflict();            // yes → refuse
await db.query("INSERT INTO …");                       // no → take it
```

An agent will write this for you on request, and it will pass every test you give it. You may also have added a loading spinner or disabled a submit button to stop double submissions — a real improvement to the user experience, and **not** a fix: it defends against one user clicking twice, not two users arriving together, and anyone can call your API directly.

The demo app has this exact shape in its booking endpoint, which is why fifteen simultaneous requests produced fifteen bookings for one slot.

</Section>

A check tells you what *was* true. Nothing holds it true until your insert runs. The window is normally microseconds — but it only has to be wide enough once, and anything you `await` inside it (a payment pre-check, an external call) widens it to hundreds of milliseconds.

### The four classic races

| Race | Shape | Consequence |
|---|---|---|
| **Double booking** | Check availability → insert | Two customers, one slot |
| **Double charge** | Check if paid → charge | Refund, support ticket, lost trust |
| **Negative inventory** | Count sold → sell | Oversold stock |
| **Lost update** | Read → modify → write | Someone's work silently gone (L7.6) |

### Four ways to fix it, in order of preference

**1. Let the database enforce the rule (a constraint).** Best, because it's impossible to bypass — not from your code, not from a worker, not from someone in `psql` at 2am.

For "this exact combination may exist once", a unique constraint:

```sql
ALTER TABLE payments ADD CONSTRAINT payments_event_unique UNIQUE (provider_event_id);
```

For "these time ranges may not overlap", an **exclusion constraint** — the right tool for bookings, and the one almost nobody knows exists:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
  ADD COLUMN hours int4range
    GENERATED ALWAYS AS (int4range(start_hour, end_hour)) STORED;

ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (room_id WITH =, date WITH =, hours WITH &&);
```

Now an overlapping insert fails at the database, whatever the application believes:

```text
ERROR: conflicting key value violates exclusion constraint "bookings_no_overlap"
DETAIL: Key (room_id, date, hours)=(1, 2026-12-01, [20,22)) conflicts with
        existing key (room_id, date, hours)=(1, 2026-12-01, [19,21)).
```

Note the range semantics: `int4range(19,21)` is `[19,21)` — end-exclusive. A booking ending at 21 and one starting at 21 **don't** overlap, which is exactly what you want for consecutive bookings.

**2. Make the write itself conditional** so the check and the act are one statement:

```sql
-- Sell a ticket only if capacity remains. One statement, no window.
UPDATE events SET sold = sold + 1
 WHERE id = $1 AND sold < capacity
RETURNING sold;
```

If it returns no row, there was no capacity. The condition is evaluated and the write applied atomically.

**3. Lock the thing you're about to change** (`SELECT … FOR UPDATE`) — serialises the two requests so one waits for the other. Correct, costs throughput, and it's L7.4's subject.

**4. Serializable isolation** — the database detects the conflict and aborts one transaction, which you then retry. Powerful, needs retry logic, and it's L7.3's subject.

<Callout type="key">
**Prefer a constraint over application logic, always.** Application checks protect one code path; a constraint protects the data. Your app, your worker, a future endpoint an agent writes, a migration script and your own `psql` session are all subject to it. The question to ask is never "does my code check this?" but **"what makes this impossible?"**
</Callout>

### Handling the constraint violation gracefully

Adding a constraint turns a silent data corruption into a loud error, which you then translate into a sensible response:

```ts
try {
  await db.query("INSERT INTO bookings (…) VALUES (…)", [...]);
} catch (e) {
  // 23P01 = exclusion violation, 23505 = unique violation
  if (e.code === "23P01" || e.code === "23505") {
    return NextResponse.json({ error: "slot already booked" }, { status: 409 });
  }
  throw e;
}
```

Keep the application's pre-check too — it gives a fast, friendly 409 in the common case. The difference is that it's now an *optimisation*, not the guarantee.

<Section kind="tools">

| Mechanism | Enforces | Use for |
|---|---|---|
| `UNIQUE` constraint | This combination exists at most once | Idempotency keys, one-vote-per-user, slugs |
| **`EXCLUDE USING gist`** | These ranges don't overlap | Bookings, reservations, schedules |
| `CHECK` constraint | A row-level invariant | `sold <= capacity`, `end_hour > start_hour` |
| Conditional `UPDATE … WHERE` | Decision + write in one statement | Counters, inventory, state transitions |
| `SELECT … FOR UPDATE` | Serialise access to specific rows | Multi-row invariants (L7.4) |
| `SERIALIZABLE` isolation | The database detects all conflicts | Complex invariants (L7.3) |
| Redis `SETNX` / `INCR` | Atomic claim or counter outside Postgres | Rate limits, distributed locks |
| Unique index on an expression | Uniqueness over computed values | `UNIQUE (lower(email))` |

What good looks like: for every business rule of the form "at most one", "no overlap", or "never more than N", you can name the **database object** that enforces it. If the only answer is "the code checks it", you have the ticketing startup's architecture.

The migration caution: adding a constraint to a table that already violates it fails. Find the violations first (query in step 2 above), decide what to do with them — they're real data corruption, and deciding is a product question — then add the constraint. On a large table, `ALTER TABLE` takes a lock, so see L7.4 and M6.3 before doing it in production.

</Section>

<Section kind="break-fix">

**Symptom:** A subscription product gives each new user one free trial credit. Support reports that a handful of users have multiple trial credits, and one has eleven. Revenue is being given away, slowly.

<Evidence title="the code">

```ts
// POST /api/trial/claim
const user = await db.query("SELECT id FROM users WHERE id=$1", [userId]);

const existing = await db.query(
  "SELECT id FROM credits WHERE user_id=$1 AND kind='trial'", [userId]);
if (existing.rows.length > 0) {
  return NextResponse.json({ error: "trial already claimed" }, { status: 409 });
}

const eligible = await checkEligibility(userId);     // external fraud API, ~400ms
if (!eligible) return NextResponse.json({ error: "not eligible" }, { status: 403 });

await db.query(
  "INSERT INTO credits (user_id, kind, amount) VALUES ($1,'trial',10)", [userId]);
return NextResponse.json({ ok: true });
```

</Evidence>

<Evidence title="the data and the pattern">

```text
SELECT user_id, count(*) FROM credits WHERE kind='trial' GROUP BY 1 HAVING count(*)>1;
 user_id | count
---------+-------
    4417 |    11
    8823 |     3
    9120 |     2
   (14 rows total)

SELECT user_id, created_at FROM credits WHERE user_id=4417 AND kind='trial' ORDER BY created_at;
 2026-11-02 14:22:08.113
 2026-11-02 14:22:08.147
 2026-11-02 14:22:08.182
 ... (11 rows, all within 400ms)

Schema:
  credits(id serial pk, user_id int, kind text, amount int, created_at timestamptz)
  -- no unique constraint anywhere

Client: a "Claim trial" button with no disabled state during the request.
Logs: 11 × "POST /api/trial/claim 200" for user 4417, all within 400ms.
```

</Evidence>

Name the shape, explain the 400ms, and give the fix that makes eleven credits impossible rather than unlikely.

<Reveal label="Reveal the cause">

**Check-then-act, with a 400ms external call sitting inside the window.**

**The mechanism.** All eleven requests ran the `SELECT` on `credits` before any of them reached the `INSERT`. Each found zero rows and concluded the trial was unclaimed — correctly, at the moment it looked. Then each spent ~400ms in `checkEligibility`, and all eleven inserted.

**The 400ms is the whole story.** Normally the check-to-act window is sub-millisecond and you'd need freak timing to hit it. Here an `await` on a third-party API holds the window open for 400ms — easily long enough for a user to land eleven requests in it by holding down a key, double-clicking an unguarded button, or a retrying mobile client on a flaky connection. The timestamps confirm it: all eleven within 400ms, matching the eligibility call exactly. **Anything awaited between a check and its act turns a theoretical race into a reproducible one.**

**Why the obvious fixes are insufficient:**
- *Disable the button* — fixes one user double-clicking; does nothing for a direct API call, a retrying client, or two tabs.
- *Move the eligibility check before the credits check* — narrows the window but doesn't close it. Still check-then-act.
- *Wrap it in a transaction* — a transaction alone does **not** help here. Under Postgres's default read-committed isolation, two transactions can both run that `SELECT`, see nothing, and both insert. Transactions give you atomicity, not mutual exclusion (L7.3 covers exactly this misconception).

**The fix — make it impossible in the database:**

```sql
-- One trial credit per user, enforced by the data itself.
CREATE UNIQUE INDEX CONCURRENTLY credits_one_trial_per_user
  ON credits (user_id) WHERE kind = 'trial';
```

A **partial** unique index: it constrains only trial rows, leaving users free to hold many credits of other kinds. Then translate the violation:

```ts
try {
  await db.query("INSERT INTO credits (user_id, kind, amount) VALUES ($1,'trial',10)", [userId]);
} catch (e: any) {
  if (e.code === "23505") {
    return NextResponse.json({ error: "trial already claimed" }, { status: 409 });
  }
  throw e;
}
```

Also **move the expensive eligibility call before the insert but treat the insert as the authority**, and keep the pre-check as a fast path for the friendly common case.

**Clean up the existing damage deliberately:** fourteen users have extra credits. Decide the product answer (revoke the extras? honour them?) before writing the migration, because the unique index won't apply until the duplicates are gone — and deleting rows that represent money is not a decision to make inside a migration script.

**The general rule, restated:** when the invariant is "at most one of these may exist", express it as a unique index, not as an `if`. Then the guarantee holds against your endpoint, a future endpoint, a worker, a backfill, and a 2am `psql` session — none of which will remember to run your check.

</Reveal>

<Section kind="checklist">

For every rule your product promises:

- What **database object** enforces it? (Not "the code checks it".)
- Is the invariant "at most one"? → unique index (partial, if conditional)
- Is it "no overlap"? → exclusion constraint with `btree_gist`
- Is it "never more than N"? → conditional `UPDATE … WHERE n < limit`, or a `CHECK`
- Is there an `await` between the check and the write? (That's the window, measured in hundreds of milliseconds.)
- Does the application translate the constraint violation into a sensible status code?
- Is there a concurrent test asserting the invariant holds under N simultaneous requests?

Before adding a constraint in production:

- Find existing violating rows first, and decide what to do with them as a product question.
- Use `CREATE UNIQUE INDEX CONCURRENTLY` on large tables to avoid a long lock (M6.3).
- Ship the error-handling code *with* the constraint, or you convert silent corruption into 500s.

What good looks like: every "at most once" rule maps to a named constraint; application pre-checks exist for friendly messages and are understood to be optimisations; a disabled submit button is UX, never a correctness measure.

Red flags: "the code checks it" as the guarantee; a transaction added in the belief it prevents duplicates; UI-level double-submit protection described as a fix.

</Section>
