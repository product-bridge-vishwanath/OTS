<Section kind="story">

A team of three grew to a team of nine over a year. Nobody decided how secrets would be managed — they just accumulated, the way they always do: a few in the Vercel dashboard, a few pasted into a shared "keys.txt" in a private Slack channel because it was faster than asking, the database password in a pinned message from fourteen months ago, and one contractor's laptop that still has `.env` files for a project they left in March.

When that contractor's access was supposed to be revoked, nobody could answer a simple question: **which secrets did they ever see?** Nothing had been rotated since launch. The database password was the same one from the first `docker compose up`. The honest answer was "we don't know what they have, so we have to assume all of it" — followed by a weekend spent rotating nine secrets across four services, several of which nobody remembered required a restart on *two* different processes to take effect.

Nothing had leaked. The problem was that nobody could prove that, and proving it cost a weekend they didn't plan for.

</Section>

<Section kind="already-did">

You've pasted a secret into a platform dashboard (Vercel, Render, Railway) and trusted it from then on — reasonably, for a solo project. You may have shared a key with a cofounder over Slack or a text message, meaning to "set it up properly later." If you've never had to answer "who has access to this, and when did we last change it," you've never actually needed a secret manager yet — which is normal, and this lesson is about recognizing the point where that stops being true.

</Section>

<Section kind="mental-model">

An environment variable in a platform dashboard *is* secret storage — for one person, one project, with no audit trail and no rotation plan. A **secret manager** is what you add when any of three things becomes true: more than one person needs access, you need to know *who* accessed *what* and *when*, or secrets need to change on a schedule rather than only when something goes wrong.

### What a secret manager actually adds

| Without one | With one |
|---|---|
| Secrets live wherever they were pasted — dashboards, `.env` files on laptops, chat history | One source of truth; apps and people fetch from it, never copy it around |
| "Who has access?" has no answer | Access is a list you can read |
| "Did anyone open this?" has no answer | An audit log you can query |
| Rotation means a manual hunt across every place a secret was ever pasted | Rotation is a workflow: issue, propagate, verify, revoke |
| Revoking one person's access means rotating everything they might have seen | Revoking is scoped to what that person's access actually covered |

### The rotation mechanics most people get wrong

Rotation isn't "change the value." It's a sequence with an overlap window, because a running process somewhere is always mid-request with the old value:

1. **Issue** a new secret alongside the old one — most providers let both be valid simultaneously for exactly this reason.
2. **Propagate** the new value to every consumer (every service, every environment that uses it).
3. **Verify** every consumer is actually using the new value — not "I set it," but confirmed from logs or the provider's own usage attribution.
4. **Revoke** the old value only after verification. Revoking before verifying turns a planned rotation into an outage.

<Callout type="warn">
**Database credentials are the hard case.** An API key rotation is stateless — the next request just uses the new key. A database password rotation has to account for every already-open connection, every connection *pool* holding cached credentials, and every worker that only reads the credential at boot. Reversing step 3 and 4 here (revoking before every pool has cycled) is the single most common self-inflicted outage in this lesson's territory. Cloud-native secret managers that integrate with the database (AWS Secrets Manager's RDS rotation, for instance) automate exactly this sequencing — which is the strongest argument for paying for one once a database password needs to rotate on a schedule.
</Callout>

</Section>

<Section kind="tools">

| Tier | Tool | Fits when |
|---|---|---|
| Platform-native | Vercel/Render/Railway environment variables | Solo project, single owner, no rotation schedule — the floor, not a long-term plan |
| Team-shared vault | **Doppler**, **1Password** (Secrets Automation), Infisical | A team needs shared access with *some* control; syncs out to platform env vars so apps don't change |
| Cloud-native, IAM-scoped | **AWS Secrets Manager**, GCP Secret Manager, Azure Key Vault | Already on that cloud; access is controlled the same way as everything else (IAM), and database rotation can be automated |
| Dynamic secrets, deep audit | **HashiCorp Vault** | Compliance requirements, secrets that should be generated per-lease and expire automatically, or infrastructure complex enough to justify running (or buying) a dedicated secrets system |

**The honest guidance by stage:** a solo founder is fine on platform-native env vars until the first time they need to answer "who has access." A small team with shared secrets should move to Doppler or 1Password before that question comes up, not after. A team already deep in one cloud should prefer that cloud's native secret manager over a generic one, because IAM access control and audit logging come for free. Vault earns its operational cost only when dynamic, short-lived secrets or strict compliance are real requirements — introducing it earlier adds a system to operate without a problem it's solving yet.

</Section>

<Section kind="hands-on">

```bash
cd demo-app && docker compose up -d --build
```

The demo app's rotatable secret is `ANTHROPIC_API_KEY`. Even without a real secret manager installed, practice the four-step sequence on it — the motion is identical whether you're editing a `.env` file or clicking "rotate" in a vault's UI.

1. **Confirm the current value** the running process has (never print the whole value):
   ```bash
   docker compose exec app sh -c 'echo "${ANTHROPIC_API_KEY:0:8}… (${#ANTHROPIC_API_KEY} chars)"'
   ```

2. **Issue**: set a new value in `demo-app/.env` without removing the old line yet — write it as a comment so you can see both:
   ```bash
   # .env
   # OLD (do not delete yet): ANTHROPIC_API_KEY=sk-ant-old-FAKE0000
   ANTHROPIC_API_KEY=sk-ant-new-FAKE1111
   ```

3. **Propagate and verify** — recreate the container (env changes need a restart, per M1.5) and confirm the *running process*, not just the file, has the new value:
   ```bash
   docker compose up -d app
   docker compose exec app sh -c 'echo "${ANTHROPIC_API_KEY:0:12}…"'
   #   Must show the NEW prefix. If it still shows old, the container wasn't recreated.
   docker compose logs --tail 20 app | grep -i assistant   # any recent calls succeeded on the new value
   ```

4. **Revoke** — in real life, this is the step where you'd go to the provider's dashboard and disable the old key *now that step 3 has confirmed nothing still needs it*. Delete the commented-out old value from `.env` as the equivalent here.

5. **Now do the harder version**: the worker and the app are two separate services in `compose.yaml`. Check whether a secret you rotate needs to reach both:
   ```bash
   docker compose exec worker env | grep -i anthropic   # it isn't there — the worker never needed it
   ```
   The lesson here isn't about this specific variable; it's the habit of asking **which services actually consume this secret** before declaring a rotation complete. A secret manager with dependency tracking answers this for you; without one, you have to know your own services' env lists.

</Section>

<Section kind="break-fix">

**Symptom:** A planned database password rotation, announced in advance and done during a low-traffic window, causes a five-minute full outage anyway. The team swears they "did it in the right order."

<Evidence title="the runbook they followed">

```text
1. Generate new DB password in provider console.      [done 14:00]
2. Update DATABASE_URL in web app's env, redeploy.     [done 14:02, redeploy confirmed healthy]
3. Revoke old password in provider console.            [done 14:03]
4. Done.
```

</Evidence>

<Evidence title="production logs, 14:03–14:08">

```text
14:03:11  worker  ERROR  password authentication failed for user "app_user"
14:03:11  worker  ERROR  connection pool: 0/10 connections available
14:04:40  worker  cron job "nightly-report" FAILED — could not connect
14:06:02  app     WARN   connection pool refilling, 3/10 healthy
14:08:15  app     INFO   connection pool: 10/10 healthy
```

</Evidence>

<Evidence title="services using DATABASE_URL">

```text
$ grep -rl DATABASE_URL compose.yaml
app:     DATABASE_URL: postgres://...
worker:  DATABASE_URL: postgres://...
#   two services, ONE redeploy happened
```

</Evidence>

Why did the "redeploy confirmed healthy" app have no outage, while the worker — never mentioned in the runbook — broke for five minutes?

<Reveal label="Reveal the cause">

**The runbook rotated the secret for one of two consumers and revoked the old password before the second consumer, the worker, had ever received the new one.**

The web app was redeployed with the new `DATABASE_URL` in step 2 — that's a genuine, verified propagation. The worker was never touched, because it wasn't in anyone's mental model of "the database password" even though its `compose.yaml` entry has the identical variable. When step 3 revoked the old password, the worker's existing connections — opened with the old credential — started failing the moment Postgres rejected re-authentication attempts on them, and its connection pool had nothing valid to refill with until someone redeployed it too.

**Why "redeploy confirmed healthy" gave false confidence:** it confirmed the *app* was healthy. It said nothing about the worker, because nobody checked the worker, because the runbook's step 2 named only one service by habit — the one people think of as "the app."

**The fix:**
1. **Propagate to every consumer before revoking anything** — the actual rule from this lesson's mental model, which the runbook silently narrowed to "every consumer we remembered."
2. Before the next rotation, run the audit from this lesson's hands-on: `grep` every compose service (or every platform service) for the variable name, and treat that list as the propagation checklist, not memory.
3. For database credentials specifically, prefer a rotation path that re-establishes connections gracefully (a pool that retries with the new credential, or a provider's automated dual-validity rotation) over a manual two-step runbook with a human-remembered consumer list.
4. Add a health check *per service* to the rotation runbook, not one shared "the app is up" check.

**The transferable rule:** "propagate to every consumer" requires first knowing the full, mechanical list of consumers — not the list a person can recall under runbook pressure. The worker was always a consumer; it was only forgotten.

</Reveal>

</Section>

<Section kind="checklist">

Moving a secret from a dashboard into a managed store:

- Does more than one person, or more than one environment, need access? That's the trigger — not "we have money for tools now."
- Is access scoped per secret/project, matching who actually needs it, rather than one shared master credential?
- Is there an audit log you could actually produce if asked "who accessed this, and when"?

Rotating any secret:

- Issue the new value alongside the old (don't revoke yet).
- Propagate to **every** consumer — found by grepping for the variable name across every service and environment, not by memory.
- Verify each consumer is confirmed using the new value, from logs or provider attribution, not from "I redeployed."
- Revoke the old value only after every consumer is verified.
- For database credentials specifically: confirm existing connections and pools are accounted for, not just new ones.

Red flags: a rotation runbook with one verification step covering several services; "we rotated it" meaning only the service someone happened to think of; a shared vault password that gives everyone access to everything; no record of who can currently read a given secret.

</Section>
