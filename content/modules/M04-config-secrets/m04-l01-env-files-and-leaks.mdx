<Section kind="story">

A solo founder asked their agent to "commit everything and push, I want this backed up." The agent ran `git add -A`. The repo had no `.gitignore` yet — this was day one — and `.env` went up with it, live Stripe secret key included, to a public GitHub repository.

GitHub's secret scanning caught it in about ninety seconds and emailed Stripe directly, under a partner program most founders have never heard of. Stripe disabled the key before the founder even saw GitHub's own alert. It was the best possible outcome of the worst possible mistake.

Three weeks later, a different founder asking a different agent to "push my changes" had no such luck. The leaked key belonged to a provider with no scanning partnership, the repo had already been forked twice by bots that watch GitHub's public commit firehose for exactly this pattern, and the first anyone knew was a $4,200 overage alert nine hours later.

Same mistake. Wildly different outcomes — and the difference had nothing to do with how careful either founder was *after* the commit.

</Section>

<Section kind="already-did">

You have run `cp .env.example .env` on day one of nearly every project. You have told an agent to "commit my changes" or "push this" without checking what "everything" included. You have probably seen a `.gitignore` get added to a repo on day *three*, after the `.env` file already existed — which, as this lesson explains, is one commit too late.

You may also have received a secret-scanning alert email from GitHub or GitLab and not fully understood what it meant, or why the advice was "rotate the key" rather than "delete the file."

</Section>

<Section kind="mental-model">

M1.5 covered where environment variables live and why `.env` never reaches production on its own. This lesson is about the other direction: how a value that was only ever meant to sit in a local, gitignored file ends up somewhere you never intended — and why the fix is never "remove it."

### The one fact that explains everything here

**Git doesn't store files. It stores every version of every file, forever, by default.** "Deleting" a line in a new commit doesn't erase it — it adds a commit that says "don't show this anymore," while the original commit, containing the original bytes, stays in the repository's history where `git log`, `git show`, and anyone with a clone can still read it.

`.gitignore` does not interact with history at all. It only tells Git "don't track changes to this path from now on." If `.env` was ever committed even once — even in a commit you later "fixed" — adding it to `.gitignore` afterward does nothing to that old commit.

### Public vs private: a difference of degree, not of safety

A public repo is scraped so fast that "notice before it's used" is rarely realistic. A private repo buys you time, not immunity — it can be forked by a collaborator, cloned to a laptop that's later compromised, made public by a future "let's open-source this" decision, or exposed by a breach at GitHub or GitLab itself. Treat "it was private" as a reason you *might* have more time to respond, never as a reason the key is still safe.

<Callout type="key">
**Rotate first, always.** Issuing a new key and revoking the old one is mandatory and always sufficient. Scrubbing the commit from history is optional, often difficult, and on its own does nothing — anyone who already has the old commit (a fork, a clone, a CI cache, a bot) still has the secret regardless of what your `main` branch looks like now.
</Callout>

</Section>

<Section kind="tools">

| Need | Tool | What it actually does |
|---|---|---|
| Prevent the file from being tracked | `.gitignore` + a committed `.env.example` | Stops future commits only — the baseline, not a fix for history |
| Catch a secret before it's committed | `gitleaks`/`trufflehog` as a pre-commit hook | Pattern-matches known key formats locally, before `git push` even exists as an option |
| Catch a secret before it's pushed | GitHub push protection | Blocks the push itself when a recognizable secret pattern is detected — the best point in the timeline to stop it |
| Find out after the fact | GitHub/GitLab secret scanning (repo or org-wide) | Scans existing history and alerts; for partnered providers (Stripe, many cloud providers), alerts the *provider* directly |
| Remove a secret from history | `git filter-repo` (or BFG Repo-Cleaner) | Rewrites every commit to strip the file/string — changes every commit hash downstream, breaks other people's clones, and is pointless if a copy already escaped |

**The ordering that matters:** push protection (before it leaves your machine) beats secret scanning (after it's already out) beats history rewriting (after it's already out *and* probably copied). Most teams only ever install the third one, which is the least effective of the three because by the time it fires, rotation is the only tool left anyway — so you may as well treat rotation as the plan from the start.

</Section>

<Section kind="hands-on">

```bash
cd demo-app
cp .env.example .env
```

1. **Confirm `.env` is actually ignored, don't assume it.**
   ```bash
   git check-ignore -v demo-app/.env
   git status demo-app/.env       # should show nothing — ignored, not untracked-and-pending
   ```
   `git check-ignore -v` prints *which* rule in *which* file is doing the ignoring — useful the day a `.gitignore` rule is subtly wrong (e.g. `.env` ignored but `.env.production` isn't).

2. **See why a `.gitignore` added today can't save yesterday's mistake**, in a disposable scratch repo (never do this in a real project):
   ```bash
   mkdir -p /tmp/leak-demo && cd /tmp/leak-demo && git init -q
   echo "ANTHROPIC_API_KEY=sk-ant-demo-FAKEKEY00000000000000" > .env
   git add .env && git commit -q -m "add env config"
   echo ".env" > .gitignore
   git rm --cached .env -q && git add .gitignore && git commit -q -m "stop tracking .env"
   git log -p --all -- .env | grep -A1 ANTHROPIC_API_KEY
   #   The fake key is still right there, in the first commit, forever.
   cd - && rm -rf /tmp/leak-demo
   ```

3. **Run a secret scan** over the demo app (install `gitleaks` or use `docker run` if you don't have it locally):
   ```bash
   gitleaks detect --source . --no-git -v 2>/dev/null || echo "install gitleaks to run this: https://github.com/gitleaks/gitleaks"
   ```

4. **Do the rotation motion** on the demo app's real (optional) secret, so the muscle memory is in your hands before you ever need it under pressure:
   ```bash
   # "issue" a new key value (in real life: generate it in the provider's dashboard)
   #   edit demo-app/.env — change ANTHROPIC_API_KEY to a new value
   docker compose up -d --build
   docker compose exec app sh -c 'echo "${ANTHROPIC_API_KEY:0:12}…"'   # confirm the NEW value is what the running process has
   #   only after confirming the new value is live would you revoke the old one at the provider
   ```
   This is the whole rotation shape: issue new → deploy → verify the running process has it → *then* revoke old. L4.2 covers why that order matters even more once a database is involved.

</Section>

<Section kind="break-fix">

**Symptom:** A SaaS founder gets an email: "Unusual activity detected on your OpenAI-compatible API key." The dashboard shows 40x normal spend starting nine hours ago. Nothing in the app changed recently, as far as the founder knows.

<Evidence title="the provider dashboard">

```text
Usage, last 24h:  14.2M tokens  (daily average: 310K tokens)
Requests from IP ranges: 3 unrecognized ranges, none matching the app's host
First unrecognized request: 09:14 UTC
```

</Evidence>

<Evidence title="git log, searched for the key's known prefix">

```text
$ git log -p --all -S "sk-proj-7fQ2" | head -20
commit 4a1c9e2 (origin/main, 3 weeks ago)
    chore: add local env setup for new contributor
+OPENAI_API_KEY=sk-proj-7fQ2xK9mLwYvN4Rt8pQeZcVbHj3nFgTa
...
commit 8b22f10 (4 days ago)
    fix: remove accidentally committed env file
-OPENAI_API_KEY=sk-proj-7fQ2xK9mLwYvN4Rt8pQeZcVbHj3nFgTa
```

</Evidence>

<Evidence title="repository visibility">

```text
Repository: public (was private until 5 days ago — made public for a hackathon submission)
Forks: 2 (both created the day it went public)
```

</Evidence>

The founder's question: "I already removed it four days ago — why is it still being used?"

<Reveal label="Reveal the cause">

**The key was committed three weeks ago, the repo went public five days ago, and "removing" it four days ago only removed it from the latest snapshot — not from the two commits that still contain it in full, both now sitting in two public forks.**

Walk the timeline: the key sat harmlessly in a *private* repo's history for over two weeks — not safe, just not yet exposed to anyone who'd look. The moment the repo was made public for the hackathon, that history became readable by anyone, including the automated scanners that watch GitHub's public firehose for exactly this key-prefix pattern. Within hours, at least one scraper had it. The commit that "removed" the key four days *later* changed nothing for whoever already copied it in those first few hours — and it changed nothing for the two forks, which carry their own full copy of history regardless of what happens on the original repository afterward.

**Why "I removed it" felt like it should have worked:** the founder was reasoning about the *current file*, which genuinely no longer contains the key. The exposure lives in the *commits*, which the removal commit doesn't touch, and in the *forks*, which `git filter-repo` on the original repo can't touch at all.

**The fix, in order:**
1. **Rotate the key now.** Generate a new one, deploy it, confirm the running app uses it, revoke the old one at the provider. This alone stops the bleeding regardless of how many copies exist.
2. **Check the damage** via the provider's usage logs: which endpoints, how much spend, any data exposed by what those requests returned.
3. **Decide whether to scrub history** — worthwhile for keeping the repo clean going forward, but explicitly *not* a security control once a key has escaped. Note it won't reach the forks.
4. **Add push protection and a pre-commit scan** so the next "add local env setup" commit never gets this far.
5. If the repo must stay public, audit anything else committed under its *private* period with the same scrutiny — visibility changes don't just affect the future.

**The transferable rule:** a secret's exposure is decided by its full commit history and every clone/fork of it, not by what the latest commit on `main` currently contains. "I deleted it" is a statement about files; a leak is a statement about history.

</Reveal>

</Section>

<Section kind="checklist">

Before trusting a repository with any secret, even briefly:

- Does `.gitignore` cover `.env` and every `.env.*` variant, and is it in place *before* the first `.env` file is ever created?
- Is there a committed `.env.example` with placeholder values, so nobody needs the real file to know what's required?
- Is push protection (or at minimum pre-commit scanning) actually installed, not just planned?
- Has anyone run a full-history scan at least once, including on repos that pre-date these controls?

If a key may have leaked:

- Rotate it — immediately, before investigating anything else.
- Check the provider's usage logs for misuse during the exposure window.
- Treat "repo was private" as "had less time to be found," never as "was safe."
- Treat a fork or old clone as a permanent copy that a history rewrite on the original repo cannot reach.
- Decide on history scrubbing only after rotation, as cleanup, not as the fix.

Red flags: "I deleted the line, so it's fine now"; a `.gitignore` added in the same PR that first introduces secrets, instead of before; an agent told to "commit everything" with no review of what that includes.

</Section>
