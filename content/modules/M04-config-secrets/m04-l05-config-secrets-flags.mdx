<Section kind="story">

A product had a genuine emergency: a bug in the booking confirmation flow was double-charging customers, and the fix needed a few hours of engineering. The fastest safe response was to disable the online checkout path entirely and take bookings by phone until the fix shipped.

The team reached for what they had: an environment variable, `CHECKOUT_ENABLED=false`. Correct instinct, wrong mechanism. Changing it meant editing the platform dashboard, then redeploying — and the redeploy pipeline, untouched in months, failed its first run on an unrelated dependency warning that had been silently accumulating. Fixing *that* took forty minutes. The double-charging bug kept charging customers for forty minutes longer than the "instant" kill switch was supposed to allow, because the kill switch wasn't instant — it was a deploy wearing a disguise.

Three weeks earlier, in an unrelated decision, the same team had put a **feature flag service row** behind their checkout experiment, flippable from a database update with no deploy at all. Nobody connected the two until the postmortem: they'd already built the right mechanism, for the wrong use case, a few files away from where they actually needed it.

</Section>

<Section kind="already-did">

You've set an environment variable that was really a secret (M4.1–M4.3) and one that was really just config, in the exact same `.env` file, with no distinction between them. You've probably also reached for "add an env var" as the default answer to "how do we make this configurable," because it's the first tool most people learn — and for genuine config, it's usually the right one.

</Section>

<Section kind="mental-model">

M1.5 introduced this table once, briefly, as a landing point after explaining env var mechanics. This lesson is the decision framework behind it — the question to ask *before* you reach for an env var, a secret store, or a flag.

### The one question that sorts almost everything

**Would you need to redeploy to change this safely during an incident?**

- If the answer is "no, and that's fine" — it's **config**. `PORT`, `LOG_LEVEL`, a retry count, a page size. Safe to commit a placeholder, safe to read from an env var, safe to be visible in the running process's environment.
- If the answer is "no, but it must never be visible to anyone unauthorized" — it's a **secret**. A database URL, an API key, a signing key. Same delivery mechanism as config (an env var, read at boot) but a completely different handling rule: never committed, access-controlled, rotated (L4.1–L4.3).
- If the answer is "yes, and that's the problem" — it's a **feature flag**, and belongs somewhere that can change *without* a deploy: a database row, a dedicated flag service, a remote config endpoint checked at request time or on a short poll interval.

### Why "it's just a boolean, I'll use an env var" is the recurring mistake

An env var *is* a legitimate way to store a flag's value — for flags that genuinely don't need to change without a deploy, like a flag gating a feature that only ever gets turned on once, permanently, at launch. The mistake is using it for a flag whose entire purpose is "change this fast, under pressure, by someone who may not have deploy access at 2am." If the honest answer to "how fast could you flip this" is "as fast as a deploy," you don't have a kill switch — you have a deploy with extra steps, and M14.2 is explicit that rollback, not a flag redeploy, should be the first move in a real incident anyway.

<Callout type="key">
A feature flag only earns its name if flipping it is **faster and safer than a deploy.** A database-backed flag checked on each request (or cached for seconds, not minutes) qualifies. An env var requiring a container restart does not — it's config that happens to hold a boolean.
</Callout>

</Section>

<Section kind="tools">

| Need | Where it lives | Why |
|---|---|---|
| Config (non-secret, deploy-time is fine) | Env var, `.env.example` documented | M1.5's territory — cheap, visible, restart-bound, and that's fine |
| Secret | Env var from a secret store (L4.2), never committed | Same delivery, different handling: access control, rotation, no plaintext in git |
| A flag turned on once, permanently, at launch | Env var is acceptable | No incident will ever need it flipped faster than a deploy |
| A kill switch / gradual rollout / A-B test | A flag service (**LaunchDarkly**, **Unleash**, **Statsig**, **GrowthBook**) or, minimally, a database table read on each request | Must change without a deploy — that's the entire point of calling it a "flag" |
| "We just need one boolean, a whole flag service is overkill" | A single `flags` table (`key text primary key, enabled boolean`), checked per request with a short in-memory cache | The honest minimum viable version — still beats an env var because it's mutable at runtime |

**The staged answer, same shape as L4.2's secret-manager guidance:** a solo project with one or two flags that rarely change is fine with a database table. A team running experiments, gradual rollouts, or per-user targeting outgrows a hand-rolled table and should move to a dedicated service — not because the table is wrong, but because targeting rules and rollout percentages are themselves a small product a dedicated tool has already built.

</Section>

<Section kind="hands-on">

```bash
cd demo-app && docker compose up -d --build
```

1. **Classify everything the demo app currently reads from the environment.** For each one, apply the redeploy question:
   ```bash
   grep -rhoE "process\.env\.[A-Z0-9_]+" --include="*.ts" --include="*.js" app/ lib/ worker/ \
     | sed 's/process\.env\.//' | sort -u
   ```
   Sort each into config, secret, or "this is actually a flag in disguise." (In the current demo app, everything present is genuinely config or secret — `POOL_MAX`, `REPORT_EVERY_MINUTES` are config; `DATABASE_URL`, `ANTHROPIC_API_KEY` are secrets. There's no flag yet, which is the point of the next step.)

2. **Add a real kill switch**, the mechanism the opening story needed and didn't have, for the assistant feature specifically:
   ```sql
   -- demo-app/db/init.sql (or a migration)
   CREATE TABLE IF NOT EXISTS flags (key text PRIMARY KEY, enabled boolean NOT NULL DEFAULT true);
   INSERT INTO flags (key, enabled) VALUES ('assistant_enabled', true) ON CONFLICT DO NOTHING;
   ```
   In `app/api/assistant/route.ts`, check it before calling the model:
   ```ts
   const { rows } = await db.query("SELECT enabled FROM flags WHERE key = 'assistant_enabled'");
   if (rows[0]?.enabled === false) {
     return NextResponse.json({ answer: "The assistant is temporarily unavailable.", model: "disabled" });
   }
   ```

3. **Prove it's actually instant** — no restart, no redeploy, no `docker compose up`:
   ```bash
   docker compose exec -T db psql -U ots -d demo -c \
     "UPDATE flags SET enabled = false WHERE key = 'assistant_enabled';"
   curl -s localhost:3001/api/assistant -X POST -H 'Content-Type: application/json' \
     -d '{"question":"test"}' | python3 -m json.tool
   #   → "temporarily unavailable", with NOTHING redeployed
   docker compose exec -T db psql -U ots -d demo -c \
     "UPDATE flags SET enabled = true WHERE key = 'assistant_enabled';"
   ```
   Compare this to M1.5's step 2 (`POOL_MAX` requiring `docker compose up -d app` to take effect) — same "change a value" action, structurally different speed, because one lives in the process's environment and the other lives in the database.

</Section>

<Section kind="break-fix">

**Symptom:** During a real incident — a third-party payment provider outage — an on-call engineer tries to flip `PAYMENTS_ENABLED` to show customers a "pay by phone" message instead of a broken checkout. The flip doesn't take effect for eleven minutes, by which point the provider's outage has already resolved on its own.

<Evidence title="how the flag was implemented">

```ts
// lib/flags.ts
export const PAYMENTS_ENABLED = process.env.PAYMENTS_ENABLED !== "false";
```
```yaml
# compose.yaml (production equivalent: platform dashboard)
app:
  environment:
    PAYMENTS_ENABLED: "true"
```

</Evidence>

<Evidence title="the on-call engineer's timeline">

```text
14:02  Provider outage confirmed via status page
14:03  Set PAYMENTS_ENABLED=false in platform dashboard
14:03  (dashboard shows "saved" — engineer believes this is done)
14:14  Still seeing checkout attempts hit the dead provider in logs
14:14  Engineer realizes: dashboard env var change requires a redeploy to take effect
14:14  Triggers redeploy
14:17  Redeploy completes, checkout now correctly shows "pay by phone"
14:19  Provider status page reports resolved
```

</Evidence>

What's the actual failure here, and is it the engineer's mistake?

<Reveal label="Reveal the cause">

**`PAYMENTS_ENABLED` was implemented as an environment variable — config's delivery mechanism — for something that was, by definition, a kill switch. It inherited config's restart-bound update model, which is exactly wrong for the one property a kill switch needs: speed, under pressure, with no deploy in the loop.**

This isn't the engineer's mistake. They did the right thing in the right order — identified the outage, reached for the switch, flipped it — and the mechanism itself added an eleven-minute tax that erased the entire value of having a switch at all. By the time the fix "took," the underlying problem had already resolved on its own, meaning the kill switch contributed nothing except the false confidence of a dashboard that says "saved" while nothing user-facing has actually changed.

**The decision-tree question, applied in hindsight:** "would you need to redeploy to change this safely during an incident?" The honest answer, the moment `PAYMENTS_ENABLED` was created, was "no — that's the whole point of a payments kill switch." It was implemented with the one mechanism that answers "yes" by construction.

**The fix:**
1. **Move it to a database-backed flag** (or a real flag service, if the team runs several), exactly as this lesson's hands-on demonstrates for the assistant feature — checked per request or on a short cache, no deploy required to flip.
2. **Test the flip during a drill, not during a real incident** — the eleven minutes were discovered live; a quarterly incident drill (M14) would have caught the redeploy requirement for free.
3. **Keep the env var version too, as a secondary, slower-but-independent kill switch** — if the database itself is part of the incident, a database-backed flag can't help, and the original mechanism becomes the fallback rather than the only option. Belt and suspenders beats either alone.

**The transferable rule:** a kill switch's entire value is its speed. A mechanism that requires a deploy to change isn't a slower kill switch — functionally, it's not a kill switch at all, because the gap between "decided" and "effective" is exactly where the incident's damage keeps accruing.

</Reveal>

</Section>

<Section kind="checklist">

For any configurable value, ask in order:

1. Would changing this safely during an incident require a redeploy — and is that **acceptable**? If yes → config, an env var is fine.
2. Must it stay hidden from anyone without authorized access? If yes → secret, same delivery as config, entirely different handling (L4.1–L4.3).
3. Does it need to change **without** a deploy — a kill switch, a gradual rollout, an experiment? If yes → a feature flag, stored somewhere mutable at runtime, never an env var.

Before trusting any "flag" as an actual kill switch:

- Has flipping it been tested live, under time pressure, not just read in code?
- Does flipping it require anything that itself can fail mid-incident (a deploy pipeline, a build)?
- If the answer to either is uncomfortable, it's config wearing a flag's name.

Red flags: a boolean env var named with "enabled," "kill switch," or "toggle" that still requires a restart; a flag system so elaborate for two rarely-changed booleans that nobody maintains it; a genuinely one-time, launch-day flag routed through a full flag service for no reason.

</Section>
