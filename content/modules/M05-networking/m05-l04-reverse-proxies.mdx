<Section kind="story">

A support engineer spent forty minutes debugging a "server is down" ticket by checking the application server — logs clean, process running, health check passing when hit directly. The customer insisted the site was broken. The engineer insisted it wasn't.

Both were right. The customer was hitting the site through the public domain, which routed through a reverse proxy; the engineer was checking the app server directly, bypassing the proxy entirely without realizing it. The proxy's own configuration had a `proxy_read_timeout` of 5 seconds, and one specific endpoint had started taking 8 seconds under load that week — well within what the *application* considered a normal, if slow, response, and entirely outside what the *proxy* was willing to wait for. The app was never down. The proxy was timing out on it and returning its own 504 to the customer, a full network layer away from anywhere the engineer was looking.

Once someone thought to check from *outside*, through the actual public path, it took ninety seconds.

</Section>

<Section kind="already-did">

You've seen a platform's branded error page — "Application Error," a 502 page with a sad icon — and had no idea whether the problem was your code, your database, or something in between that you've never configured directly. If you've ever been told "your app is fine, but something in front of it isn't," you've met a reverse proxy without necessarily naming it.

M7.4 already taught you that a database can have a queue of waiting requests invisible from outside; this lesson is the same idea one layer up the stack — a proxy sitting between the internet and your app, with its own timeouts, its own opinions, and its own distinct error codes for distinct failure shapes.

</Section>

<Section kind="mental-model">

### What a reverse proxy actually does

It receives every public request, and forwards it to one of potentially several backend servers (your app). From the outside, there's one address; behind it, the proxy decides which actual server answers. This single layer does several jobs at once: TLS termination (M5.3 — the proxy often holds the certificate, talking plain HTTP to the app behind it), routing, and — the part this lesson focuses on — translating backend failures into a specific, diagnostic HTTP status.

### The three codes, and what each one eliminates

| Code | What it means | What you've just ruled out |
|---|---|---|
| **502 Bad Gateway** | The proxy tried to connect and got refused, or got a response it couldn't parse | DNS, TLS, and the proxy itself are fine — look at whether the app process is even running |
| **503 Service Unavailable** | The proxy has no healthy backend to send this to at all | Often deliberate (maintenance mode, every health check failing, autoscaler between instances) |
| **504 Gateway Timeout** | The proxy connected fine, but the app never responded within the configured wait | The app is ALIVE — look at what it's doing that's slow (M6.1's missing index, M7.4's lock wait, M7.9's unthrottled backfill) |

<Callout type="key">
**502 and 504 point you at completely different investigations, and the difference is entirely in whether the proxy's connection attempt succeeded.** A 502 means "nobody answered the phone" — check if the process exists. A 504 means "someone picked up and then said nothing" — the process is running; something *inside* it is stuck. Conflating these wastes exactly the kind of time the story's engineer spent.
</Callout>

### Verified on this exact stack

The demo app's `proxy` service (nginx, real config, in `demo-app/nginx/nginx.conf`) demonstrates both:

```text
502 — proxy_pass pointed at a port nothing listens on → connection refused
      Verified: ~17ms response, 502, immediately — no waiting, because
      refusal is instant.

504 — proxy_pass pointed at something that ACCEPTS the connection but
      never sends a response → proxy_read_timeout (5s) elapses
      Verified: exactly 5.022s, then 504 — the delay IS the timeout
      setting, not network latency.
```

That timing difference is itself diagnostic: an *instant* failure is a refused connection (502-shaped); a failure that takes exactly as long as a configured timeout is a hang (504-shaped). You can often tell which one you're looking at just by how long the error took to arrive, before reading any log at all.

<Operator>

```bash
cd demo-app
docker compose up -d --build

# ── Baseline: everything healthy through the real proxy ───────────────
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://localhost:8080/api/health

# ── Trigger a REAL 502 (nothing listening) ─────────────────────────────
sh scripts/break/proxy-upstream-down.sh
sleep 1
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://localhost:8080/
#   Verified: 502, in milliseconds — instant refusal.

# ── Trigger a REAL 504 (accepts, never answers) ────────────────────────
sh scripts/break/proxy-upstream-slow.sh
sleep 2
time curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/
#   Verified: 504, taking exactly ~5s — the configured proxy_read_timeout.

# ── Restore ─────────────────────────────────────────────────────────────
sh scripts/break/proxy-restore.sh

# ── See the proxy's own config — the timeouts that define these codes ──
cat nginx/nginx.conf | grep -E "timeout|proxy_pass"

# ── Confirm: bypassing the proxy entirely changes the picture ─────────
curl -s -o /dev/null -w "direct to app: %{http_code}\n" http://localhost:3001/api/health
curl -s -o /dev/null -w "through proxy: %{http_code}\n" http://localhost:8080/api/health
#   Both 200 normally — but during a proxy-side issue, these two can
#   disagree completely, which is exactly the engineer-vs-customer
#   confusion from the story, reproduced on your own machine.
```

</Operator>

<Section kind="break-fix">

**Symptom:** During a traffic spike, roughly 1 in 20 requests return 503. The engineering team confirms the app servers are healthy, not overloaded, and have spare capacity. The 503s stop the moment traffic drops back to normal.

<Evidence title="the load balancer's health check config">

```text
Health check path: /api/health
Interval: 10s
Timeout: 2s
Unhealthy threshold: 2 consecutive failures
Healthy threshold: 2 consecutive successes
```

</Evidence>

<Evidence title="app instance metrics during the spike">

```text
Instance A: CPU 45%, p95 latency 180ms, health check: passing
Instance B: CPU 52%, p95 latency 310ms, health check: FAILED at 14:02:11, 14:02:21
                                          PASSED at 14:02:31
Instance C: CPU 48%, p95 latency 190ms, health check: passing
```

</Evidence>

<Evidence title="what /api/health actually does">

```ts
export async function GET() {
  await db.query("SELECT count(*) FROM bookings");  // a real query, every time
  return NextResponse.json({ ok: true });
}
```

</Evidence>

Instance B has spare CPU and isn't overloaded by any obvious measure, yet its health check failed twice in a row — enough to get it pulled from rotation for twenty seconds, during which its share of traffic got 503s from the load balancer (no healthy instance to route *those specific* requests to, momentarily). Why would a healthy-looking instance fail its health check under load?

<Reveal label="Reveal the cause">

**The health check itself runs a real database query with a 2-second timeout, and under traffic-spike load the connection pool briefly had no spare connection available for the health check specifically — not because the instance was broken, but because every connection was busy serving real, successful requests at that exact moment.**

**The mechanism:** instance B's own application traffic (180-310ms p95, perfectly healthy) was legitimately using its connection pool near capacity during the spike. The health check's `SELECT count(*) FROM bookings` has to wait in line for a connection just like any other query — and if it waits more than 2 seconds because the pool is momentarily saturated with real traffic, the health check times out and *reports failure*, even though every actual user-facing request on that instance succeeded throughout.

**This is a self-inflicted wound: the health check competes with real traffic for the exact resource (M6.2's connection pool) that traffic pressure is already stressing.** The instance isn't unhealthy; the health check is measuring the wrong thing under the wrong conditions and drawing the wrong conclusion from contention it's partly causing.

**The fix, in order:**
1. **Make the health check cheap and dependency-light** for routing decisions — `SELECT 1` or no database call at all for the basic liveness check, reserving the "check I can actually reach the database" version for a separate, less time-pressured deep-check endpoint not used for second-by-second routing decisions.
2. **Give the health check its own small, reserved connection** or a short-circuit path that doesn't compete with the main pool, if a real dependency check is genuinely needed in the routing path.
3. **Raise the health check timeout slightly and require more consecutive failures** before pulling an instance — M8.8's alert-fatigue lesson applies here too: a check that can be defeated by a 2-second traffic blip isn't measuring the thing you actually care about (is this instance able to serve users), only a narrower, noisier proxy for it.

**The transferable lesson:** a health check that calls a real downstream dependency is itself a consumer of that dependency's limited capacity, and under exactly the load conditions you most want accurate health data, it can be the thing that fails first — reporting an outage that's actually just contention it's contributing to.

</Reveal>

</Section>

<Section kind="checklist">

When you see a 5xx reported by a user but can't reproduce it internally:

- Are you checking through the SAME public path the user hit (proxy/LB included), or bypassing it by checking the app server directly?
- Is it a 502 (instant, connection refused) or a 504 (delayed, matching a configured timeout)? Time it.
- If 503: is there a load balancer with a health check that could be marking an instance unhealthy for a reason unrelated to real user-facing health?

For any health check used in routing decisions:

- Does it make a real database or dependency call?
- Could that call compete with real traffic for a limited resource under exactly the load conditions you care most about?

What good looks like: 502, 503 and 504 are read as three different diagnoses pointing at three different investigations, and nobody confuses "I checked the app directly" with "I checked what the user actually experienced."

Red flags: a health check that's more expensive than the traffic it's meant to protect against false-negative-ing; debugging a user-reported 5xx exclusively from inside the app server, never from outside through the real path.

</Section>
