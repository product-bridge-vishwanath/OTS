<Section kind="story">

A developer's agent generated an endpoint for "toggling" a booking's status — flip it from pending to confirmed, or back. The agent wired it up as a `GET` request, because that's what the frontend button's `fetch()` call defaulted to and it worked immediately in testing.

Three weeks later, a browser extension that prefetches links for faster navigation — entirely standard, well-behaved software — visited the booking page, saw the toggle link, and **prefetched it**, exactly as it's designed to do for any link it encounters, because prefetching a `GET` is supposed to be free of side effects. It toggled forty bookings from confirmed to pending, silently, across several customers' browsers, with zero malicious intent anywhere in the chain. The developer spent a day convinced they'd been hacked.

Nobody was hacked. HTTP methods carry a *meaning*, not just a mechanism, and `GET` promises — to browsers, proxies, crawlers, prefetchers, caches, everyone — "reading this causes nothing to change." The code broke that promise, and every tool built on trusting it broke something in return.

</Section>

<Section kind="already-did">

You've typed a URL and had the page load — that's a `GET`. You've submitted a form and had something change — usually a `POST`. If you've used `curl` following an agent's instructions, you've probably pasted a command with `-X POST` or `-H` without fully parsing what each flag meant, and gotten a response back that was either reassuring or confusing depending on whether you could read it.

This lesson is about reading that response — and the request — the way someone experienced does: as a structured sentence with a subject, a verb, and a set of modifiers, not as a wall of text to skim past to find the status code.

</Section>

<Section kind="mental-model">

### Methods are promises, not just verbs

| Method | Promise | Safe to retry blindly? | Safe to prefetch/cache? |
|---|---|---|---|
| `GET` | Read-only, no side effects | Yes | Yes |
| `HEAD` | Like GET, headers only, no body | Yes | Yes |
| `POST` | Create/do something, may not be repeatable safely | **No** — may double-create | No |
| `PUT` | Replace a resource entirely, idempotent by definition | Yes (same result either way) | No |
| `PATCH` | Partially update a resource | Depends on the update | No |
| `DELETE` | Remove a resource | Usually yes (deleting twice = still deleted) | No |

<Callout type="key">
**"Idempotent" here means something specific and different from M7.7's meaning, worth distinguishing: an HTTP method is idempotent if making the SAME request twice produces the SAME end state as making it once** — not "safe to retry a job," but "repeating this exact call changes nothing further." `GET`, `PUT`, `DELETE` are specified as idempotent; `POST` is explicitly not. This is exactly why browsers warn before resubmitting a form (a `POST`) on back/refresh, and never warn about reloading a page (a `GET`) — and it's exactly the promise the prefetcher in the story assumed the toggle endpoint was keeping.
</Callout>

### Reading `curl -v` as a sentence

```text
> GET /api/health HTTP/1.1          ← you, asking: "read this resource"
> Host: localhost:3001              ← which site, on a shared IP
> User-Agent: curl/8.1.2
>
< HTTP/1.1 200 OK                   ← the answer: "here it is, succeeded"
< Content-Type: application/json    ← what shape the body is in
< Content-Length: 46
<
{"ok":true,"checks":{"postgres":"ok","redis":"ok"}}
```

Lines starting `>` are what you sent; `<` is what came back. Read the request as "verb, path, protocol version" and the response as "protocol version, status, reason phrase" — everything else is a header, a labeled fact about the message.

### Headers worth actually knowing

| Header | What it tells you |
|---|---|
| `Content-Type` | How to parse the body — `application/json`, `text/html`, etc. |
| `Content-Length` | Body size in bytes — a mismatch here is a real bug signal |
| `Cache-Control` | Whether and how long this response may be cached (M5.5) |
| `Authorization` | Credentials for this request — **never log this** (M8.3) |
| `Set-Cookie` / `Cookie` | Session state, handled specially (M5.6) |
| `X-Forwarded-For` | The original client IP, when behind a proxy (M5.4) |

### Status code families, briefly (the full reference has every code)

2xx succeeded, 3xx redirected, 4xx your request was the problem, 5xx the server's side failed. The [status code reference](/reference/status-codes) is the detailed version; what matters here is recognizing the family fast enough to know which side of the connection to investigate first.

<Operator>

```bash
cd demo-app

# ── Read a request/response as a full conversation ────────────────────
curl -v http://localhost:3001/api/health 2>&1
#   Every line prefixed > is sent; every line prefixed < is received.

# ── GET vs POST, and what each promises ───────────────────────────────
curl -s http://localhost:3001/api/bookings | head -c 100; echo
curl -s -X POST http://localhost:3001/api/bookings \
  -H "Content-Type: application/json" \
  -d '{"room_id":1,"customer_name":"http-test","date":"2026-12-15","start_hour":9,"end_hour":10}'
#   The POST created a row. Running it again creates ANOTHER row — that's
#   the non-idempotent promise, kept. Clean it up after:
docker compose exec -T db psql -U ots -d demo -c \
  "DELETE FROM bookings WHERE customer_name='http-test';"

# ── See the headers alone, fast ────────────────────────────────────────
curl -sI http://localhost:3001/api/health
curl -s -o /dev/null -D - http://localhost:3001/api/bookings | head -10

# ── Timing breakdown — where did the time actually go? ─────────────────
curl -s -o /dev/null -w \
  "dns:%{time_namelookup}s connect:%{time_connect}s ttfb:%{time_starttransfer}s total:%{time_total}s\n" \
  http://localhost:3001/api/bookings

# ── OPTIONS: what methods does this endpoint actually allow? ──────────
curl -v -X OPTIONS http://localhost:3001/api/bookings 2>&1 | grep -iE "< allow|< HTTP"
```

<Section kind="break-fix">

**Symptom:** An app's "unsubscribe from emails" link, sent in every marketing email, works when clicked from the email client — but a security scanner flags it as vulnerable, and shortly after, several users report being unsubscribed without clicking anything.

<Evidence title="the link and the handler">

```html
<a href="https://app.example.com/unsubscribe?token=abc123">Unsubscribe</a>
```

```ts
// GET /unsubscribe
export async function GET(req: NextRequest) {
  const token = req.nextUrl.searchParams.get("token");
  await db.query("UPDATE subscribers SET subscribed=false WHERE token=$1", [token]);
  return NextResponse.redirect("/unsubscribed");
}
```

</Evidence>

<Evidence title="server logs for an affected user">

```text
GET /unsubscribe?token=abc123   200   (User-Agent: Mozilla/5.0 ... GmailImageProxy)
GET /unsubscribe?token=abc123   200   (User-Agent: Mozilla/5.0 ... Outlook-prefetch)
```

</Evidence>

The user never clicked the link. Two different requests for it still appear in the logs. What happened?

<Reveal label="Reveal the cause">

**The unsubscribe link is a `GET`, and email clients — Gmail's image proxy, Outlook's link prescanning for security — both fetch `GET` links automatically to prefetch images or scan for malware, exactly as they're designed to, because `GET` is supposed to be safe to fetch without asking.**

This is the identical mechanism as the story's booking toggle, in a more common, well-documented form: email clients proxy and prescan links constantly, and every reputable one does so believing `GET` requests carry no side effects — that belief is the entire HTTP specification's promise about the method. An unsubscribe action that changes state on a `GET` will be silently triggered by security scanning, image proxying, link previews, and browser prefetching, all of which are *correctly implemented* software trusting a promise this endpoint broke.

**Why the security scanner flagged it too, independently:** this is also a <Term k="idor">CSRF</Term>-adjacent concern — a `GET` request can be triggered from anywhere (an `<img src>` tag on a completely unrelated malicious page, for instance), with no user interaction and no cross-origin restriction, because browsers don't apply the same protections to simple `GET` navigation that they do to cross-origin `POST`s with credentials. A state-changing `GET` is doubly wrong: it breaks the idempotency promise AND it's trivially triggerable by a third party.

**The fix:** make the actual unsubscribe a `POST`, triggered by a confirmation page the `GET` link lands on:

```ts
// GET /unsubscribe?token=... — shows a confirmation page, changes NOTHING
export async function GET(req: NextRequest) {
  const token = req.nextUrl.searchParams.get("token");
  return renderConfirmationPage(token);   // "Click to confirm unsubscribe"
}

// POST /unsubscribe — the actual state change, from a real user click
export async function POST(req: NextRequest) {
  const { token } = await req.json();
  await db.query("UPDATE subscribers SET subscribed=false WHERE token=$1", [token]);
  return NextResponse.json({ ok: true });
}
```

This is standard practice specifically because of this failure mode — nearly every unsubscribe flow you've used that shows a confirmation page before actually unsubscribing exists for exactly this reason, not as unnecessary friction.

**The transferable rule:** anything that changes state must never be reachable by `GET` alone, because you don't control who or what issues `GET` requests to your app — browsers, crawlers, scanners, proxies and prefetchers all assume they can, freely, because the specification tells them they can.

</Reveal>

<Section kind="checklist">

For every endpoint in your product:

- Does a `GET` or `HEAD` request ever change data? (It must not, ever, no exceptions.)
- Is the method chosen by what it promises (idempotent? side-effect-free?) rather than by what was easiest to wire up?
- Would a prefetcher, crawler, or automated link scanner trigger this unexpectedly if it found the URL?

What good looks like: you can state, for any endpoint, which HTTP method it uses and why that method's specific promise is the right one for what it does — and `curl -v` output reads as a sentence, not a wall of text.

Red flags: a "toggle" or "delete" or "unsubscribe" action reachable via `GET`; a frontend's `fetch()` default method chosen without considering what it implies; status codes read without distinguishing which family they're in.

</Section>
