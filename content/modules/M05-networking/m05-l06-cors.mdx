<Section kind="story">

A developer split his app into a frontend (deployed on Vercel) and a backend API (deployed separately on Render), following an agent's suggestion to "separate concerns." Locally, on `localhost`, everything worked — frontend and backend both ran on `localhost`, different ports, and the browser let it through without complaint.

The moment he deployed both pieces, every API call from the frontend failed with a console error he'd never seen before: `blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`. He pasted the exact request into `curl` to debug it — and it worked perfectly, every time, no error at all.

That inconsistency is the whole lesson in miniature: **CORS is enforced by the browser, not the server, and not the network.** `curl` has no concept of "origin" and never checks this header at all — it simply isn't a client that enforces the policy. The server was always answering correctly; the browser was the only party in the room applying a rule that `curl` had never agreed to follow.

</Section>

<Section kind="already-did">

You've hit this error. Nearly everyone who's split a frontend and backend across different domains or ports has seen `blocked by CORS policy` at least once, usually right after a deploy that worked fine locally. You've probably also been confused that the exact same request works from Postman or `curl` — which feels like it should mean the server is fine, and it does mean that; it just doesn't mean what you assumed it meant about the browser.

</Section>

<Callout type="key">
**The response always arrives at the browser — CORS doesn't stop the network request or hide server data from the network. It stops JavaScript from reading the result.** This is why opening the Network tab shows you a `200` with a real body even on a "CORS error" — the data got there; the browser just refused to let your script touch it. And it's exactly why CORS is a browser-only concern: it exists to protect a *user's browser* from a malicious page silently reading data from sites the user is logged into, not to protect your server from unwanted traffic (that's a different job — authentication, and rate limiting).
</Callout>

### Simple requests vs. preflighted requests

A `GET` with no custom headers, or a `POST` with a simple content type, is a "simple request" — the browser just sends it and checks the response header. Anything more interesting (a custom header, `Content-Type: application/json` on some setups, `PUT`/`DELETE`) triggers a **preflight**: the browser sends an `OPTIONS` request *first*, asking permission, before sending the real one.

<Callout type="warn">
**A 204 response to an `OPTIONS` request does NOT mean CORS is configured.** Verified on the demo app: Next.js answers every `OPTIONS` request automatically with `204` and an `Allow` header listing supported methods — this looks like a successful preflight and grants **nothing**, because it contains no `Access-Control-Allow-Origin` at all. The browser checks for that specific header; a 204 with the wrong headers (or missing ones) still fails the real request that follows.
</Callout>

### The three headers that actually implement CORS

```ts
// This is the minimum that actually grants cross-origin access —
// not just answering OPTIONS, but answering it with the RIGHT headers.
export async function OPTIONS(req: NextRequest) {
  return new NextResponse(null, {
    status: 204,
    headers: {
      "Access-Control-Allow-Origin": "https://partner-widget.example.com",
      "Access-Control-Allow-Methods": "GET",
    },
  });
}

export async function GET(req: NextRequest) {
  const res = NextResponse.json({ rooms: [...] });
  res.headers.set("Access-Control-Allow-Origin", "https://partner-widget.example.com");
  return res;
}
```

**`Access-Control-Allow-Origin` must be set on both the preflight AND the real response** — setting it only on one is a common half-fix that looks right until tested against an actual browser.

### Cookies and `SameSite`: a related, separate rule

`SameSite` controls whether a cookie is sent on a *cross-site* request at all — a different mechanism from CORS, often confused with it because both involve "is this request from somewhere else."

| Value | Cookie sent on cross-site requests? |
|---|---|
| `Strict` | Never — not even clicking a link from another site |
| `Lax` (the modern default) | On top-level navigation (clicking a link), not on background `fetch`/XHR |
| `None` | Yes, always — but **requires `Secure`** (HTTPS only) |

A cross-site API call that needs to carry a session cookie needs `SameSite=None; Secure` on the cookie **and** `Access-Control-Allow-Credentials: true` **and** a specific (not wildcard `*`) `Access-Control-Allow-Origin` on the response — all three, together, or the browser silently drops the cookie or refuses the response.

<Operator>

```bash
cd demo-app

# ── Confirm: NO CORS headers currently exist on this API ──────────────
curl -sI -H "Origin: https://evil.example.com" http://localhost:3001/api/rooms \
  | grep -i "access-control"
#   Verified: nothing. This endpoint currently only works same-origin.

# ── The preflight trap: 204 that grants nothing ────────────────────────
curl -sI -X OPTIONS -H "Origin: https://evil.example.com" \
  -H "Access-Control-Request-Method: POST" http://localhost:3001/api/bookings
#   Verified: "204 No Content" with an "allow: GET, HEAD, OPTIONS, POST"
#   header — looks successful, but NO access-control-allow-origin at all.
#   A browser would still block the real request that follows this.

# ── Add real CORS for one allowed origin, and verify both directions ──
#   (See this lesson's hands-on for the exact code change.)
#   After adding it:
curl -sI -H "Origin: https://partner-widget.example.com" http://localhost:3001/api/rooms \
  | grep -i "access-control"
#   → access-control-allow-origin: https://partner-widget.example.com
curl -sI -H "Origin: https://evil.example.com" http://localhost:3001/api/rooms \
  | grep -i "access-control"
#   → nothing. Correctly blocked, by the ORIGIN CHECK IN YOUR CODE —
#   CORS headers don't block anything server-side; your code deciding
#   what to send based on the Origin header is what blocks it.
```

</Operator>

<Section kind="break-fix">

**Symptom:** A payment form embedded as an iframe on partner sites works everywhere except inside one specific partner's site, where submitting the form silently does nothing — no error visible to the end user, no server-side record of the attempt.

<Evidence title="the embed and the request">

```html
<!-- on the partner's site -->
<iframe src="https://payments.example.com/embed?merchant=acme"></iframe>
```

```text
# The form POSTs with credentials: 'include' to carry the session cookie
# set when the merchant's customer first authenticated.
Response headers from payments.example.com:
  Set-Cookie: session=abc123; SameSite=Lax; Secure
  Access-Control-Allow-Origin: https://partner-site.example.com
  Access-Control-Allow-Credentials: true
```

</Evidence>

<Evidence title="browser console on the failing partner site">

```text
(no error logged at all — the request appears to complete, but the
 session cookie is simply absent on the follow-up request)
```

</Evidence>

Everything in the headers looks correctly configured for cross-origin credentialed requests. Why does the cookie not make it through?

<Reveal label="Reveal the cause">

**`SameSite=Lax` does not permit the cookie to be sent on a cross-site request originating from inside an iframe — only `SameSite=None` does, and `Lax` is exactly wrong for this specific embedding pattern even though it's the modern, generally-recommended default.**

**Read the table from the mental model again, specifically for this shape:** `Lax` sends the cookie on top-level navigation (a user clicking a link to your domain) but withholds it on background requests from a *third-party context* — and a form submitted from inside an iframe embedded on someone else's page is exactly that: a cross-site request, from a context the browser doesn't trust by default. `CORS` headers (`Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials`) govern whether the *response* is readable by the embedding page's script — they say nothing about whether the *cookie* gets attached to the request in the first place. Both mechanisms have to independently agree to allow this, and here only one of them did.

**Why it worked on OTHER partner sites:** if other partners embed the same payment form differently — as a top-level redirect/popup rather than an iframe, for instance — `Lax` would be perfectly sufficient there, because top-level navigation is exactly what `Lax` permits. The failure is specific to the iframe embedding pattern, which makes "it works for most partners" a genuinely confusing, misleading signal rather than evidence the configuration is broadly correct.

**The fix:**
```text
Set-Cookie: session=abc123; SameSite=None; Secure
```
`SameSite=None` is required for any cookie that must be sent from a genuinely cross-site context like an iframe — and it **mandates** `Secure` (HTTPS-only) as a non-optional pairing; browsers will silently reject a `SameSite=None` cookie without `Secure` as well, so both must change together.

**What this doesn't fix on its own, worth checking too:** some browsers (notably Safari, under various anti-tracking features) restrict third-party cookies in iframes even with `SameSite=None; Secure` correctly set, depending on browser version and user settings. For a payment flow specifically, this is a strong argument for considering whether the embed *needs* to be an iframe with a shared session cookie at all, versus a redirect-based flow or a token-based alternative that doesn't depend on third-party cookie behavior that's actively being restricted across the browser ecosystem, with the trend only continuing.

**The transferable lesson:** CORS headers and cookie `SameSite` attributes are two **independent** gates that both have to open for a cross-origin, credentialed request to fully succeed. A correctly configured CORS response with an incorrectly configured cookie attribute (or vice versa) produces exactly this symptom — everything *looks* right on inspection of either piece alone, and the request still silently fails.

</Reveal>

<Section kind="checklist">

For any cross-origin API:

- Is `Access-Control-Allow-Origin` set on BOTH the preflight (`OPTIONS`) response AND the real response?
- Is it an exact origin or validated allowlist — never a wildcard `*` combined with credentials?
- Does a `curl -I -X OPTIONS` check actually show the CORS-specific headers, not just a generic `204`?

For any cookie that might cross origins:

- Is `SameSite` the right value for how it's actually used — `Lax` for top-level navigation, `None` (with mandatory `Secure`) for iframes or background cross-site requests?
- If using `SameSite=None`, is `Secure` also set? (Browsers reject the combination otherwise.)
- For anything embedded as an iframe: have you specifically tested in a browser, not just verified headers with curl?

What good looks like: a `curl` test and a real browser test agree, because you've checked both the CORS headers and the cookie attributes independently, rather than assuming one correct piece means the whole chain works.

Red flags: a 204 on `OPTIONS` treated as proof CORS is configured; `Access-Control-Allow-Origin: *` alongside `Access-Control-Allow-Credentials: true` (browsers reject this combination); a `SameSite=Lax` cookie expected to work inside an iframe.

</Section>
