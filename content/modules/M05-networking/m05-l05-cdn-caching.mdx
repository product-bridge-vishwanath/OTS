<Section kind="story">

A news site published a correction to a factual error in a widely-shared article. The correction went live instantly in their CMS, the database updated immediately, and for the next four hours, roughly 60% of readers kept seeing the **original, uncorrected** version — served not by their origin server, which had the fix, but by a CDN edge node somewhere that had cached the old HTML and had no reason to think it was stale.

The team had set `Cache-Control: public, max-age=14400` on that page months earlier — four hours, which had seemed reasonable for a page that rarely changed. It was exactly correct for *that* assumption and exactly wrong for "we need this specific page to be right, immediately, right now." Nobody had planned for the moment the assumption would break, because by definition you don't know which page you'll need to urgently fix until it's the one that's wrong.

The fix wasn't lowering `max-age` everywhere — that would have thrown away the entire benefit of caching for every page that didn't need the panic. It was knowing, in the moment, which single command **purges one URL from the edge**, instead of waiting out a TTL you set for an entirely different situation.

</Section>

<Section kind="already-did">

You've seen a page not update after a deploy and been told to "clear your cache" — your browser's cache, sometimes, but often actually a CDN's. You've probably also benefited enormously from a CDN without ever configuring one yourself, if your platform (Vercel, Netlify) puts one in front of your static assets automatically.

M6.5 already taught you the Redis side of caching — a server-side cache your own code reads and writes. A CDN is the same fundamental idea (a faster copy, closer to the reader, with a staleness budget) operating one layer further out, between your server and the actual internet, and it has its own completely separate cache to reason about.

</Section>

### Reading cache headers for real

```bash
curl -sI https://www.cloudflare.com/favicon.ico | grep -iE "cf-cache-status|cache-control"
```
```text
cf-cache-status: HIT
cache-control: public, max-age=0, must-revalidate
```

<Callout type="key">
**`cf-cache-status: HIT` means this specific response came from the edge, never touching the origin — the origin server has no idea this request even happened.** `MISS` means the edge asked the origin and is now caching the answer. `DYNAMIC`/`BYPASS` mean the CDN deliberately didn't cache this response at all — often correctly, for anything personalized or that must always be fresh. Reading this one header is the fastest way to know whether you're debugging the edge's cached copy or the origin's live behavior.
</Callout>

### `Cache-Control` directives that actually matter

| Directive | Meaning |
|---|---|
| `public` | Anyone (browsers, CDNs, any cache) may store this |
| `private` | Only the end user's own browser may cache it — a CDN must not |
| `no-store` | Never cache this, anywhere, ever |
| `no-cache` | Confusingly named — *may* be cached, but must be revalidated with the origin before being reused |
| `max-age=N` | Seconds this may be served from cache before it's considered stale |
| `s-maxage=N` | Like `max-age`, but specifically for shared caches (CDNs) — lets you cache longer at the edge than in a user's own browser |
| `stale-while-revalidate=N` | Serve the stale copy immediately while fetching a fresh one in the background — fast and eventually-correct |

### Purging: the lever for "I need this specific thing fixed NOW"

A TTL is a bet made in advance about how often something changes. A purge is the deliberate override for the moment that bet turns out wrong for one specific URL, right now:

```bash
# Cloudflare: purge a single URL immediately, bypassing its TTL entirely.
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"files":["https://example.com/corrected-article"]}'
```

Every CDN offers some form of this. **Know where it is before you need it** — the news site's four-hour exposure window is exactly the cost of discovering a purge button exists only after you need to click it.

<Section kind="tools">

| Need | Tool |
|---|---|
| CDN + proxy + basic DDoS absorption | **Cloudflare** — the default recommendation for most products (D14) |
| Platform-native edge caching | Vercel/Netlify's built-in CDN for static assets, zero config |
| Fine-grained purge control | Cloudflare's API (single URL, by tag, or full zone purge) |
| See what a specific response's cache status is | `curl -I` + grep for the provider's cache-status header name |

The decision worth making explicitly, per response type: **does this need to be fast-and-shared (cache aggressively, know how to purge), fast-and-private (browser-only caching), or always-fresh (`no-store`)?** The demo app's `/api/rooms` chose "cache aggressively, but in Redis, not HTTP" — a valid answer, and a deliberate one.

What good looks like: every response's caching posture (public/private/no-store, and a TTL if cacheable) is a decision someone made, not a framework default nobody checked; and the purge mechanism for your CDN is something you've located and tested *before* the day you urgently need it.

</Section>

<Section kind="break-fix">

**Symptom:** A SaaS product's pricing page shows the old price for 20 minutes after a deliberate, confirmed price change — but only for users in one specific country. Everyone else sees the new price instantly.

<Evidence title="the response headers, compared">

```text
# From a US-based request, 2 minutes after the change:
cache-control: public, s-maxage=1200
cf-cache-status: MISS
x-price-shown: 49

# From a UK-based request, same moment:
cache-control: public, s-maxage=1200
cf-cache-status: HIT
x-price-shown: 39        ← the OLD price
```

</Evidence>

<Evidence title="CDN configuration">

```text
Caching mode: Cache Everything (static + dynamic responses)
Cache key: URL only (no Vary on any header)
Edge locations: global, with per-region cache populated independently
```

</Evidence>

Both requests hit the exact same URL, with the exact same `s-maxage`. One is a cache `MISS` showing the new price; the other is a `HIT` showing the old one. Why would geography affect this?

<Reveal label="Reveal the cause">

**Each CDN edge location caches independently — the US edge had already expired and refetched the page by the time of this check; the UK edge's copy, cached a few minutes earlier, simply hadn't reached its own 1200-second expiry yet.** This isn't a bug in the CDN or a configuration error — it's the same TTL applying correctly, at each edge, on each edge's own independent clock.

**Map it onto M5.1's DNS lesson, because it's the identical shape:** a CDN's edge caches are exactly like DNS resolver caches — many independent copies, each respecting a TTL from the moment *it* fetched the value, with no synchronization between them. "Global propagation" of a cache purge has the same non-instant, staggered character as DNS propagation, for the same underlying reason: distributed, independent caches don't all refresh in lockstep just because one of them did.

**Why this specific case ISN'T actually a bug, but still needed a real fix:** the price *will* correct itself everywhere within `s-maxage`'s window, with zero intervention — this is the system working as configured, just not instantly everywhere. The real question is whether 20 minutes of a wrong price, to a subset of users, in a subset of geographies, is an acceptable cost for a price *change* specifically — and for most products, the answer for pricing (unlike, say, a blog post typo) is no, it's genuinely a correctness incident while it lasts.

**The fix for right now:** purge the specific URL explicitly, which propagates the invalidation immediately to every edge rather than waiting for each one's independent TTL to naturally elapse:
```bash
curl -X POST ".../purge_cache" --data '{"files":["https://example.com/pricing"]}'
```

**The fix going forward, for anything price-sensitive:** either lower `s-maxage` specifically on pages where a stale window has real cost (accepting more origin traffic in exchange), or — the more surgical answer — **purge as part of the price-change deploy itself**, automated, so a human doesn't have to remember to do it manually during the one moment it actually matters. The caching strategy doesn't need to change for every page; the deploy process for *this specific class* of change does.

**The transferable lesson:** a CDN is not one cache with one clock — it's many independent caches, each honoring the same TTL from a different starting moment, exactly like the many independent DNS resolvers from M5.1. "It updated for me" proves nothing about whether it's updated everywhere, and the only deterministic fix for "I need this specific thing correct everywhere, right now" is an explicit purge, not patience.

</Reveal>

</Section>

<Section kind="checklist">

For any response your product serves:

- Is its `Cache-Control` directive (`public`/`private`/`no-store`, plus a TTL) a deliberate choice, or an unreviewed default?
- For anything cached publicly: do you know the exact command to purge it from your CDN, and have you located it before needing it under pressure?
- For anything price-, content-correction-, or security-sensitive: is purging part of the automated deploy process for that class of change, rather than a manual step someone has to remember?

What good looks like: nobody discovers a CDN's purge mechanism for the first time during an actual incident; caching posture is reviewed per endpoint, not inherited blindly from a framework default.

Red flags: a personalized response with no cache directive or marked `public`; "it updated for me" treated as proof a global change has taken effect; a purge step that exists only in someone's memory, not in a runbook or an automated pipeline.

</Section>
