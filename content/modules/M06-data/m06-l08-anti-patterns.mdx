<Section kind="story">

A founder asked his AI agent to "add a notes feature to bookings, and a way to track analytics events." Forty minutes later he had a working feature, a demo to show investors, and — though nobody would notice for months — a schema with five separate problems that would each eventually cost him a production incident.

Every individual decision was locally reasonable. A jsonb column for notes was the fastest way to ship a list-of-things feature without a migration. A generic `events` table with a jsonb `payload` meant never having to migrate again when a new event type showed up. Skipping foreign keys avoided a class of migration-ordering headache. None of these were agent mistakes exactly — they're the defaults an agent reaches for when optimizing for "make this work right now," because an agent asked to ship a feature in one request has no way to know this table will hold 400,000 rows in five months, or that two people will edit the same note simultaneously, or that someone will eventually need to query "every event of type X across all time."

The schema wasn't wrong. It was **unfinished** — missing the five questions nobody asked because nobody was looking far enough ahead to ask them.

</Section>

<Section kind="already-did">

If you've worked through this module and M7, you've already met every anti-pattern in this lesson individually — in the demo app, which plants them deliberately, and in your own product, almost certainly, because they're the default output of "make a working feature fast." This lesson's job is different: it's the **checklist for reading a new schema**, agent-generated or your own, and catching all five before they're load-bearing in production rather than after.

</Section>

### Anti-pattern: the everything-in-one-table log

The demo app's `events` table (planted anti-pattern AP5) is the shape:

```sql
CREATE TABLE events (
  id         serial PRIMARY KEY,
  type       text NOT NULL,
  payload    jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

This *looks* flexible — any event type, any shape of data, no migration ever needed for a new kind of event. The cost shows up in three ways, all of which M6.1's break-fix already demonstrated directly: no column can be meaningfully indexed for most real queries (the data you'd filter on is buried inside `payload`, M6.1's expression-index problem); the table grows forever with every event type mixed together, so "all bookings created last week" requires scanning rows that are 95% unrelated event types; and nothing enforces what `payload` actually contains for a given `type` — a typo in one event's shape is invisible until code that reads `payload.booking_id` gets `undefined` from a row that used `bookingId` instead.

**The fix**, if the table is worth keeping generic (an audit log genuinely benefits from this shape): add indexes on what you actually query (`type`, `created_at`, and a GIN index on `payload` if you query inside it), and seriously consider **dedicated tables for high-volume or frequently-queried event types** — `events` for the long tail of rare things, `booking_events` or similar for the type you query constantly. You don't have to choose one shape for everything.

### Anti-pattern: missing foreign keys

The demo app's `bookings.room_id` (planted anti-pattern AP3) has no foreign key to `rooms.id`. The practical consequence isn't abstract:

```sql
-- Nothing stops this. The row inserts successfully.
INSERT INTO bookings (room_id, customer_name, date, start_hour, end_hour)
VALUES (9999, 'ghost booking', CURRENT_DATE, 10, 12);
-- room_id 9999 doesn't exist. This booking can never be displayed with a
-- room name, can never be billed correctly, and nothing in the schema
-- says this is wrong.
```

<Callout type="key">
**A foreign key is a constraint the database enforces regardless of which code path writes the row** — your API, a migration script, a backfill, an agent's generated code, a manual `psql` fix at 2am. Skipping it doesn't remove the requirement that `room_id` point somewhere real; it just moves the enforcement from "guaranteed by the database" to "hoped for by every future piece of code that touches this table," forever.
</Callout>

```sql
ALTER TABLE bookings ADD CONSTRAINT bookings_room_fk
  FOREIGN KEY (room_id) REFERENCES rooms(id);
```

On an existing table with real data, this can fail the same way M6.3's `NOT NULL` migration failed — if any orphaned rows already exist, the constraint can't apply until you've decided what to do with them (a real product decision, not a technical one: delete them, reassign them, or create a placeholder room to absorb them).

### The audit habit: five questions for any schema

Run these against a new table — yours, or one an agent just generated — before it has real traffic:

| Question | Catches |
|---|---|
| Does any jsonb/array column get **appended to** by more than one request? | The single-cell anti-pattern (M7.6) |
| Will this table's query patterns still work at 100x the current row count? | Missing indexes (M6.1) |
| Does every foreign-looking column (`*_id`) have an actual `REFERENCES`? | Missing foreign keys |
| Does any column hold file bytes rather than queryable data? | Files-in-database (M6.6) |
| Is there a generic `type`/`payload` table that's actually several different things wearing one disguise? | The everything-in-one-table log |

<Operator>

```bash
cd demo-app

# ── Run the audit against the demo app's REAL schema ──────────────────
#   Q1: jsonb columns, and whether application code appends to them
docker compose exec -T db psql -U ots -d demo -c "
  SELECT table_name, column_name FROM information_schema.columns
   WHERE data_type='jsonb' AND table_schema='public';"
#   Verified: three hits — events.payload, bookings.notes, bookings.meta.
#   Not all jsonb is the anti-pattern; check which ones are APPENDED TO:
grep -rn "notes.push\|\.push(" --include="*.ts" app/ 2>/dev/null
#   Verified: only bookings.notes is appended to by application code
#   (app/api/bookings/[id]/notes/route.ts) — that's AP1, the real risk.
#   bookings.meta is written whole, once, at insert time — it's a
#   legitimate whole-value jsonb column (the mental model's exception),
#   not a hit. The audit surfaces candidates; judgment decides which
#   ones are actually the anti-pattern.

#   Q2: tables with real traffic and zero indexes beyond the primary key
docker compose exec -T db psql -U ots -d demo -c "
  SELECT t.relname, count(ix.indexrelid) - 1 AS extra_indexes
    FROM pg_class t JOIN pg_index ix ON t.oid = ix.indrelid
   WHERE t.relkind='r' AND t.relname NOT LIKE 'pg_%'
   GROUP BY t.relname ORDER BY extra_indexes;"
#   Verified: bookings, events, payments, reports, rooms all show 0 extra
#   indexes — every one has only its primary key. AP4, confirmed directly.

#   Q3: *_id columns with no matching foreign key constraint
docker compose exec -T db psql -U ots -d demo -c "
  SELECT c.table_name, c.column_name
    FROM information_schema.columns c
   WHERE c.column_name LIKE '%_id' AND c.table_schema='public'
     AND c.table_name IN ('bookings','payments','reports','events')
     AND NOT EXISTS (
       SELECT 1 FROM information_schema.key_column_usage kcu
        WHERE kcu.table_name = c.table_name AND kcu.column_name = c.column_name
          AND kcu.constraint_name != c.table_name || '_pkey');"
#   Verified hits: bookings.room_id, payments.booking_id (genuine FK gaps —
#   AP3) and payments.provider_event_id (a false positive worth knowing
#   about: it's an external string id from the payment provider, not a
#   same-database foreign key candidate at all — the audit finds every
#   *_id column with no FK; deciding which ones SHOULD have one is still
#   a judgment call).

#   Q4: file-shaped data in columns
docker compose exec -T db psql -U ots -d demo -c "
  SELECT table_name, column_name, data_type FROM information_schema.columns
   WHERE data_type IN ('bytea') AND table_schema='public';"
#   Verified: none in the demo app — it correctly has no files-in-DB anti-pattern.

#   Q5: a generic type/payload table doing several jobs
docker compose exec -T db psql -U ots -d demo -c "
  SELECT type, count(*) FROM events GROUP BY type;"
#   Verified: 'booking.created' and 'page.viewed' in the SAME table — two
#   genuinely different kinds of thing (a business event vs. an analytics
#   ping) sharing one schema with no enforced shape per type — AP5.
```

</Operator>

<Section kind="tools">

| Need | Tool |
|---|---|
| Find jsonb columns across a schema | `information_schema.columns WHERE data_type='jsonb'` |
| Find tables with weak index coverage | `pg_index` joined to `pg_class`, as in the Operator block |
| Find missing foreign keys | `information_schema.key_column_usage` cross-checked against `*_id` columns |
| Visualize a schema quickly | `pg_dump --schema-only`, or a GUI (TablePlus, Supabase's schema view) |
| Catch these at generation time | A prompt that explicitly asks the agent to justify each of the five questions, not just "add this feature" |

What good looks like: before any new table goes into production, someone has run the five-question audit against it — not relying on noticing the problem later, in an incident, the way M7.6 and M6.1's stories both did.

<Section kind="break-fix">

**Symptom:** A product's `events` table — the generic, everything-in-one-table shape — has grown to 40 million rows over 18 months. A new feature needs to query "all password-reset events for a given user, ordered by time" for a security audit page. The query is correct SQL and takes 11 seconds.

<Evidence title="the table and the query">

```sql
CREATE TABLE events (
  id serial PRIMARY KEY, type text NOT NULL,
  payload jsonb, created_at timestamptz DEFAULT now()
);

SELECT * FROM events
 WHERE type = 'password_reset_requested'
   AND payload->>'user_id' = '88213'
 ORDER BY created_at DESC;
```

```text
 Seq Scan on events  (actual time=0.031..10982.442 rows=4 loops=1)
   Filter: ((type = 'password_reset_requested'::text)
             AND ((payload ->> 'user_id'::text) = '88213'::text))
   Rows Removed by Filter: 39,999,996
```

</Evidence>

<Evidence title="attempted fix">

```sql
CREATE INDEX idx_events_type ON events (type);
-- EXPLAIN again:
 Bitmap Heap Scan on events  (actual time=0.891..2104.117 rows=4 loops=1)
   Recheck Cond: (type = 'password_reset_requested'::text)
   Rows Removed by Filter: 612,004   -- still filtering 612k rows by jsonb lookup
   ->  Bitmap Index Scan on idx_events_type  (actual time=0.412..0.412 rows=612008)
```

</Evidence>

Adding an index on `type` cut the time from 11 seconds to 2 — real, but not enough for a page a security team will use interactively. Why isn't this index sufficient, and what's the actual fix?

<Reveal label="Reveal the cause">

**The index on `type` narrows 40 million rows to 612,000 matching that one event type — still far too many to filter the rest of the way by a jsonb field extraction with no index backing it, which is still a full scan of those 612,000 rows.**

**This is the everything-in-one-table anti-pattern meeting real scale.** `password_reset_requested` is one of presumably dozens of event types sharing this table, and it alone has accumulated 612,000 rows over 18 months — common enough that indexing just the `type` column still leaves a six-figure scan for the second filter condition. The `payload->>'user_id'` extraction has no index at all, so Postgres must decode the jsonb and do a text comparison on every one of those 612,000 rows, every time this query runs.

**Two real fixes, not mutually exclusive:**

**1. A composite or expression index matching the exact query shape** (M6.1's rule, applied to jsonb):
```sql
CREATE INDEX CONCURRENTLY idx_events_type_user
  ON events (type, (payload->>'user_id'));
```
This serves the query directly — equality on `type`, equality on the extracted field — and should bring the query down to milliseconds. It's a real, valid fix, and often enough on its own.

**2. The more durable fix, worth doing for any event type queried this way routinely:** give password-reset events (and any other security-relevant, frequently-queried type) their **own table** with real columns instead of a jsonb blob:
```sql
CREATE TABLE password_reset_events (
  id bigserial PRIMARY KEY,
  user_id integer NOT NULL REFERENCES users(id),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON password_reset_events (user_id, created_at DESC);
```
Now `user_id` is a real, indexed, foreign-keyed column — not a string pulled out of a blob — and the query that was 11 seconds becomes a straightforward indexed lookup with none of the jsonb extraction overhead at all, ever, regardless of how large this specific table or the generic `events` table independently grow.

**Why keep `events` around at all, then?** For the genuinely generic, low-volume, rarely-queried-by-content tail — `page.viewed`, one-off diagnostic events, anything where "fits in one flexible table" outweighs "needs to be fast to query." The anti-pattern isn't having a generic events table; it's using **only** a generic events table for everything, including the event types that turn out to matter enough to deserve their own shape.

**The transferable lesson:** "flexible schema, no migrations needed" is a real benefit early, and it has a real expiration date tied to volume and query frequency — not a fixed row count, but the moment any specific event type inside the blob becomes common enough or important enough to need its own index. The fix at that point isn't abandoning the generic table; it's **promoting the event types that earned it** into their own properly-indexed, properly-typed tables, while the long tail stays where it was.

</Reveal>

<Section kind="checklist">

The five-question audit, for any new or existing table:

1. Does a jsonb/array column get appended to by more than one request? → single-cell risk (M7.6)
2. Will current query patterns hold at 100x the row count? → index risk (M6.1)
3. Does every `*_id` column have a real `REFERENCES`? → orphan risk
4. Does any column hold file bytes instead of queryable data? → storage risk (M6.6)
5. Is a generic type/payload table actually several different things in disguise? → scaling-by-type risk

Before accepting any agent-generated schema:

- Have you asked it to justify each of the five questions explicitly, rather than just reviewing the result?
- For any foreign key you're about to add retroactively, have you checked for existing orphaned rows first?
- For any generic table, is there a plan for promoting high-volume event types to their own table once they earn it?

What good looks like: every new table is checked against the five questions before it has real traffic, not discovered to be missing one of them during an incident months later — which is how three of this module's other lessons' stories all began.

Red flags: "we'll add indexes/foreign keys later if we need them" as the plan; a generic events table whose busiest event type has never been given its own index or table; an agent-generated schema accepted without anyone asking it the five questions.

</Section>
