<Section kind="story">

A founder's app let users upload profile photos. The upload endpoint received the file, and — because it was the obvious thing to do with the tools he had — wrote the image bytes into a `bytea` column in Postgres, next to the user's other data. It worked. It shipped. For eight months, nobody noticed anything wrong.

Then his database backup, which used to take four minutes, started taking fifty. His database bill, flat for months, tripled in a quarter with no increase in users. His "list all users" query — a page used constantly by the admin dashboard — started timing out, because it was reading and discarding megabytes of image data on every row just to display a name and an email.

He eventually moved the photos to S3. The migration took an afternoon. The fix wasn't clever — it was recognizing that a database and a file store solve different problems, and he'd been asking the wrong one to do both jobs for eight months because nobody had told him there was a second tool.

</Section>

<Section kind="already-did">

You've uploaded a file to an app and had it "just work," without knowing whether it landed in a database, a server's local disk, or something else entirely. If you've deployed to a platform that wiped your uploads on the next deploy — a real, common surprise — you've already met the reason object storage exists: **a server's local filesystem is not durable storage**, especially not on a platform that replaces the server on every deploy (M1.1's shape distinction, applied to files instead of connections).

</Section>

<Section kind="mental-model">

### What object storage actually is

Not a filesystem, not a database — a flat space of **keys and values**, where the value is a blob of bytes (a file) and the key is a string path like `avatars/user-8812.jpg`. You `PUT` a key, you `GET` a key, there's no "directory" in any real sense (the slashes in keys are cosmetic, not a folder structure the storage engine enforces), and there's no querying *inside* a file the way SQL queries inside a row.

<Callout type="key">
**The test for whether something belongs in object storage rather than a database column:** is it a blob of bytes you serve whole, rather than data you query, filter, or join? A photo, a PDF, a video, a CSV export — object storage. A user's name, a product's price, anything you'll `WHERE` on — the database. Storing a file *in* the database (as the founder's story did) works until the file volume grows, and then it costs you in backup time, query performance, and bill size, all three at once.
</Callout>

### Public vs. private, and why "private" needs a signed URL

A bucket (or a key within it) is either world-readable or it isn't. Public is right for things anyone should see without permission — a product image on a storefront. Private is right for anything tied to one user's access — an invoice, a document, a video only paying subscribers should reach.

Private storage can't just hand out a permanent URL, because that URL would itself become the access control (anyone who gets the link gets the file, forever). The fix is a **signed URL** — a time-limited, cryptographically-stamped link your server generates on demand:

```ts
// Generate a URL valid for 5 minutes, scoped to one object, one action (read).
const url = await getSignedUrl(s3Client, new GetObjectCommand({
  Bucket: "invoices", Key: `user-${userId}/invoice-2026-11.pdf`,
}), { expiresIn: 300 });
```

The file itself stays private in the bucket forever; the URL is the temporary exception, and it expires on its own — no code has to remember to revoke it.

Storing a gigabyte costs roughly the same whether it's downloaded zero times or a million. **Egress — data leaving the bucket to a user's browser — is billed per byte transferred, and it's the line item that turns a quiet $4/month bucket into a four-figure surprise** if something you store becomes popular, gets hotlinked, or is accidentally made public and scraped at scale. This is exactly why D14 (CDN/WAF) and D9 (file storage) treat egress pricing as a first-class comparison criterion between providers — some (notably Cloudflare R2) charge zero egress specifically to compete on this exact bill.

### CDN in front: for speed, and as an egress shield

Putting a CDN (M5.5) in front of a bucket does two jobs at once: it serves files from a location near the user (faster), and it absorbs repeat requests for the same popular file at the edge — so the *origin bucket* sees far less egress traffic, because the CDN is answering most requests from its own cache instead of fetching from the bucket every time.


<Section kind="tools">

| Need | Option | Note |
|---|---|---|
| General object storage | **AWS S3** | The ecosystem default; egress is billed |
| Zero-egress alternative | **Cloudflare R2** | S3-compatible API, no egress fee — the direct answer to this lesson's bill surprise |
| Platform-native, simple | **Vercel Blob, Supabase Storage** | Less setup, often pricier at real scale |
| CDN in front | Cloudflare, CloudFront, Fastly | Caches at the edge, shields origin egress |
| Image-specific transforms | Cloudinary, imgix, or a CDN's built-in resize | Resizing/format conversion on the fly, not stored per-variant |

D9 in the decision library covers the full storage-provider comparison including concrete egress pricing; D14 covers CDN choice. The decision worth making explicitly before writing any upload code: **where do files live, who can read them, and for how long does a link work** — three answers, written down, not improvised per-endpoint.

What good looks like: no file content lives in a database column; every private file is served through a short-lived signed URL, never a permanent public link; and egress cost is a number someone has actually calculated against real or projected traffic, not assumed to be negligible.

</Section>

<Section kind="hands-on">

Without live object storage in the demo stack, this is a design exercise against your own product (or a realistic plan for the demo app, if you don't yet have one).

1. **Audit for the founder's mistake.** Does anything in your product store file bytes in a database column? If so, estimate: how much has that table grown, and what does it cost your backup time and query performance (M6.1, M6.4) right now?

2. **Classify every file type your product handles** — user uploads, generated reports, static assets — as public or private, and write down who should be able to read each one.

3. **Design the signed-URL flow** for one private file type: what generates the URL, how long is it valid, and what happens if someone tries to reuse it after expiry (it should simply fail — verify that's actually true for whichever provider you'd use).

4. **Do the egress arithmetic** for your actual or projected traffic: average file size × expected downloads/month, compared against your chosen provider's per-GB egress price. Is it negligible, or is it a line item that deserves attention before launch rather than after the first bill?

5. **Decide, in writing**, whether a CDN sits in front of your bucket, and why — for speed, for egress reduction, or both.

</Section>

<Section kind="break-fix">

**Symptom:** A company's S3 bill jumped from $12/month to $4,100 in one billing cycle. Nothing about their upload feature changed. Support has received zero new complaints.

<Evidence title="the billing breakdown">

```text
S3 Storage:  $12.40    (unchanged from last month)
S3 Data Transfer OUT:  $4,089.60    (last month: $3.10)

Transfer volume this month: 81.2 TB
Top requested object: product-images/hero-banner-4k.png (18MB)
  Requests for this object: 4,511,203
```

</Evidence>

<Evidence title="the bucket's access logs">

```text
Top 5 referrer domains for this object:
  (none/direct)           3,890,112
  totally-unrelated.io      412,088
  image-aggregator.net      201,004
  myapp.com                   7,999   ← the ACTUAL site
```

</Evidence>

<Evidence title="bucket configuration">

```text
Bucket policy: public-read (set at creation, 8 months ago, never revisited)
CDN in front: none — the bucket URL is linked directly in the app's HTML
CORS: * (any origin allowed)
```

</Evidence>

4.5 million requests for one hero image, almost none from the actual site. What happened, and what's the fix?

<Reveal label="Reveal the cause">

**The bucket is public with no CDN in front and no access restriction, so the single highest-traffic image got hotlinked by other sites, and every one of their visitors' browsers downloaded the full 18MB file directly from this company's bucket, billed as egress.**

**The mechanism.** `image-aggregator.net` and `totally-unrelated.io` are serving pages that `<img src>` directly to this company's S3 URL — "hotlinking," which costs the hotlinker nothing and costs the *origin* every byte of transfer. With no CDN absorbing repeat requests at the edge and no referrer restriction on the bucket, every single one of those 4.5 million requests went straight to S3 and was billed in full, at 18MB each — that arithmetic alone is roughly 81TB, matching the bill exactly.

**Why this specific object:** an 18MB "4k hero banner" is an unusually large asset to serve raw and unoptimized in the first place — this is also, separately, a performance problem (M9.8) independent of who's requesting it. Large + publicly linkable + no CDN is close to the worst combination for egress risk.

**The fix, layered:**

1. **Put a CDN in front of the bucket immediately.** This alone solves most of the bill: repeat requests for the same object get served from edge cache, and the *bucket's* egress drops to roughly the CDN's cache-miss rate instead of every single visitor.
2. **Add a referrer or signed-URL restriction** so the asset only serves to requests originating from `myapp.com` (if there's no legitimate reason for other sites to embed it) — most CDN and storage providers support this directly.
3. **Compress and resize the image properly.** An 18MB hero banner should likely be served as a few hundred KB in an efficient format (WebP/AVIF) with responsive sizing — fixing this caps the *damage per request* even if some hotlinking persists.
4. **Set a billing alert** on data transfer specifically, not just total spend — a transfer spike is the leading indicator (M8.4's saturation signal, applied to a cloud bill instead of a server resource) that would have caught this on day two instead of at the end of the billing cycle.

**The transferable lesson:** a public bucket is public to *everyone's* pages, not just your own — and object storage egress is priced per byte with no natural ceiling, so a single popular asset with no CDN and no access restriction can turn into the single largest line item on your infrastructure bill, driven entirely by traffic you never asked for and didn't benefit from.

</Reveal>

</Section>

<Section kind="checklist">

For any file your product handles:

- Does it belong in object storage (served whole) or a database (queried, filtered, joined)?
- Is it public or private, and is that the deliberate choice rather than the default?
- If private, does access go through a signed, time-limited URL — never a permanent link?
- Is there a CDN in front of anything served frequently or publicly?
- Have you calculated egress cost against real or projected traffic, using the provider's actual per-GB price?
- Is there a billing alert on data transfer specifically?

What good looks like: no file bytes live in a database column; every private asset is reached through a signed URL with a deliberate expiry; a CDN sits in front of anything public and popular; and the egress number has been calculated, not assumed.

Red flags: images or PDFs stored as `bytea`/BLOB in a database; a public bucket with no CDN and no referrer restriction; a storage bill that surprises anyone; a signed URL with no expiry or an expiry nobody chose on purpose.

</Section>
